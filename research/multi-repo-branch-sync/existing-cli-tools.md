## 1. Landscape inventory

**Context for this section.** The requirement is a tool that, from one command, fetches and fast-forwards the major branches (`main`/`master`/`release*`) of a fixed set of local git checkouts on macOS, non-interactively. This inventory lists every candidate found; the later sections judge them against that requirement. Facts marked "(not verified)" could not be confirmed from the tool's own docs during this research pass and should be treated as unknown, not as true.

A first landscape search ([LibHunt gita alternatives](https://www.libhunt.com/r/gita), [frontaid/git-cli-tools list](https://github.com/frontaid/git-cli-tools)) confirms the field splits into three families, and that split matters more than any single feature:

1. **Registered-list / directory-scan runners** (gita, mu-repo, gitup, gitbatch, gws, git-bulk, gr, mani) — they operate on repos you already have, which is exactly the "set of local git repo directories" the developer has. Best natural fit.
2. **Manifest / workspace tools** (myrepos, tsrc, vcstool, Google repo, west, meta, mgit) — they own the checkout layout from a manifest file; they can update existing checkouts but expect to have cloned them.
3. **Forge-driven bulk tools** (ghorg, git-xargs, all-repos) — they enumerate repos from GitHub/GitLab APIs and clone/patch them; primarily for org-wide clone or org-wide code changes, not for keeping hand-chosen local checkouts fresh.

Summary from the same search: gita shows a consolidated status view and batch-executes git commands over registered repos, including recursive directory add and auto-grouping ([nosarthur/gita README](https://github.com/nosarthur/gita)); mu-repo "helps you execute the same commands in multiple git repositories" ([fabioz/mu-repo](https://github.com/fabioz/mu-repo)); git-xargs is a Gruntwork tool that applies a script across many GitHub repos in parallel via goroutines and opens PRs ([git-xargs](https://github.com/gruntwork-io/git-xargs)).

## 2. Default-branch handling

**Why this section matters.** The requirement has four hard parts: (a) pick the right major branch per repo (`main` vs `master` vs `release/*`), (b) fast-forward only, (c) never touch a dirty working tree, (d) ideally update branches that are not currently checked out (so the human can stay on a feature branch while `main` is refreshed). Almost every tool below only does "run `git pull` in each repo on whatever branch is checked out", which fails (a), (c) and (d) by construction. Findings per tool follow.

### 2.1 Per-tool notes (running list)

**mu-repo.** The commands page documents `mu upd` as "Fetches changes for the current branch and compares the current branch with the fetched changes (using WinMerge or meld)" — a preview/diff tool aimed at an interactive GUI merge, not an unattended updater ([mu-repo commands](https://fabioz.github.io/mu-repo/commands/)). Serial vs parallel is a setting (`mu set-var serial=0|1`). No documented fast-forward-only mode, no documented dirty-tree guard, and update scope is the current branch only. Everything else (`mu up`, `mu pull`) is a pass-through of the same git subcommand to every registered repo, so any FF-only or dirty-skip behaviour must come from git itself (e.g. `mu pull --ff-only`), and git's own `pull --ff-only` will still refuse (non-zero exit) rather than skip when the tree is dirty and a merge is needed. Verdict on (a)/(c)/(d): no / no / no.

**myrepos (mr).** `mr update` runs "the default `git pull`" for git repos, and the update command is overridable per repo in `.mrconfig` (e.g. `update = git pull --ff-only` or any shell snippet) ([myrepos](https://myrepos.branchable.com/)). Because the per-repo `update` action is arbitrary shell, mr *can* be configured to fetch and then `git fetch origin main:main` for a non-checked-out branch — but that logic is yours to write; mr provides only the loop, the `-j` parallelism, and the "remember actions that failed offline, retry later" queue ([myrepos](https://myrepos.branchable.com/)). Verdict: (a) only via hand-written config; (b) only if you write `--ff-only`; (c) no built-in guard; (d) possible via custom `update` command. Net: mr is a scheduler for your own script, not a solution by itself, and it has had no release since 2018.

**gitup (git-repo-updater).** This is the only tool in the set whose documented default behaviour matches the requirement almost exactly. Per its README: it "will fetch all remotes in a repository" (or only the current branch's upstream with `--current-only`/`-c`), then "will try to fast-forward all branches that have upstreams configured", and it skips any branch where a fast-forward is not possible — the README names "dirty working directory" and "merge/rebase needed" as the skip reasons ([README](https://github.com/earwig/git-repo-updater)). Merges and rebases are never performed. `--fetch-only`/`-f` skips the fast-forward step; `--prune`/`-p` deletes stale remote-tracking refs ([README](https://github.com/earwig/git-repo-updater)).
Mapping to the four hard parts: (a) it does not *pick* `main`/`master`/`release*` — it fast-forwards *every* local branch with an upstream, which is a superset (feature branches with upstreams also get fast-forwarded, harmless because FF-only cannot lose commits); (b) yes, FF-only by design; (c) yes for the checked-out branch — a dirty tree causes a skip, not a stash or a merge; (d) yes — non-checked-out branches with upstreams are fast-forwarded directly (the README describes updating all upstream-tracking branches, which necessarily includes ones not checked out). Source (`src/gitup/update.py`, read in the 2026-09-07 verification pass — the package uses a `src/` layout, which is why earlier `gitup/update.py` guesses 404'd) confirms the skip behaviour and names every skip reason: `_update_branch()` prints `skipped: no upstream is tracked.`, `skipped: branch has no revisions.`, `skipped: upstream does not exist.`, `skipped: can't find merge base with upstream.`, and `skipped: not possible to fast-forward.` when the fast-forward command returns non-zero; a dirty checked-out tree is detected by matching git's own `local changes ... would be overwritten` message and is likewise reported as a skip, never stashed or merged ([src/gitup/update.py](https://raw.githubusercontent.com/earwig/git-repo-updater/main/src/gitup/update.py)). So a *diverged* non-checked-out branch is skipped with the "not possible to fast-forward" line — the expected behaviour. Fetch failures (`GitCommandError`, e.g. unreachable remote) are caught in `_fetch_remotes()`, printed as `error: <stderr>` and the function simply `return`s; `update_bookmarks()` and `update_directories()` return `None` and the module contains **no `sys.exit` and no return code** ([src/gitup/update.py](https://raw.githubusercontent.com/earwig/git-repo-updater/main/src/gitup/update.py)). The exit code therefore depends on the CLI entry point; see section 3.1 and section 6.1.

**gita.** gita is a thin, asynchronous fan-out over git. `gita fetch` and `gita pull` default to all registered repos (or a group / the current `gita context`), and "the `git` command runs asynchronously, with the exception of `log`, `difftool` and `mergetool`, which require non-trivial user input" ([README](https://github.com/nosarthur/gita)). `gita super <repos> <any git command>` and `gita shell <repos> <any shell command>` delegate arbitrary commands, and `~/.config/gita/cmds.json` lets you register your own subcommand with fields `cmd`, `help`, `allow_all` (run on all repos when none named), `disable_async`, and `shell` ([README](https://github.com/nosarthur/gita)). Mapping to the four hard parts: (a) no built-in branch selection — `gita pull` pulls whatever is checked out; (b) `gita pull` is "standard git pull behavior", FF-only is not a gita option, so you would need `gita super pull --ff-only` or a `cmds.json` entry with `"cmd": "pull --ff-only"`; (c) no dirty-tree guard is documented — but gita's `ll` view *does* expose dirtiness (`+` staged, `*` unstaged, `?` untracked, `$` stashed) and remote relationship by colour (green = in sync, yellow = behind, purple = ahead, red = diverged), so a wrapper could query before acting; (d) not built in, but `gita super <repos> fetch origin main:main` is expressible because `super` is a pass-through ([README](https://github.com/nosarthur/gita)). Error-continuation and process exit code are not documented in the README; source shows the run continues past failures and the process exits 0 regardless (see section 3.1) ([gita/__main__.py](https://raw.githubusercontent.com/nosarthur/gita/master/gita/__main__.py)). Verdict: (a) no, (b) via pass-through only, (c) no guard (but observable), (d) via pass-through only. Net: gita is the best-maintained *registered-list fan-out* in the set (Python, 2025 release), and it supplies the repo registry + parallel runner; the FF-only/branch-selection logic still has to be a one-line git incantation you hand it.

**ghorg.** Disqualifying by default for this use case. When the target directory already exists, `ghorg clone` runs `git pull` **and then `git clean`**, and the README warns in its own words: "All local changes in the cloned directory by default will be overwritten by what's on GitHub" ([README](https://github.com/gabrie30/ghorg)). `--no-clean` suppresses the clean step, but the underlying update is still a plain `git pull` on the checked-out branch — no FF-only guarantee, no dirty-tree skip, no non-checked-out branch update. `--branch` sets one branch name for the whole run, which cannot express "main here, master there, release/* over there". Verdict: (a) no, (b) no, (c) **actively destructive unless `--no-clean`**, (d) no. ghorg's real strength — enumerating a whole GitLab group including subgroups over the API and cloning it with `--concurrency` (default 25) — is a *bootstrap* capability, not a refresh capability.

**git-xargs.** Out of scope by design: it clones every target repo fresh into `/tmp`, runs a script, commits, and opens a pull request; it has no mode for operating on existing local checkouts, and its docs mention only GitHub and GitHub Enterprise, not GitLab ([README](https://github.com/gruntwork-io/git-xargs)). Verdict: not applicable to (a)–(d). Ruled out for this requirement (kept in the inventory because it is frequently named alongside the others).

**mani.** The README and the docs introduction describe `mani sync` only as "clone all repositories" / "Clone multiple repositories with a single command" with the completion line "All projects synced" ([README](https://github.com/alajmo/mani), [manicli.com](https://manicli.com/)). Neither page documents any pull or fast-forward step for repos that already exist, so mani's built-in sync does not satisfy the update requirement on its own. What mani does offer is a clean *runner*: `mani exec --all <shell>` / `mani run <task>` with `--parallel`, project tags/paths for filtering, and a manifest that `mani init` can seed by scanning for `.git` folders ([README](https://github.com/alajmo/mani)). So mani, like myrepos, is a candidate host for a custom per-repo update snippet (e.g. a task that runs `git fetch --prune && git fetch origin main:main`), not a solution by itself. Verdict: (a)–(d) only via a user-written task. Error/exit-code semantics are not documented on the pages fetched but are settled from source in section 3.1: exit 1 on any failing project unless `--ignore-errors`, which yields exit 0 ([core/errors.go](https://raw.githubusercontent.com/alajmo/mani/main/core/errors.go)).

**tsrc.** The CLI reference documents `tsrc sync` as: "If any of the repositories is not on the configured branch, but it is clean and the `--no-correct-branch` flag is NOT set, then the branch is changed to the configured one and then the repository is updated" ([tsrc CLI reference](https://your-tools.github.io/tsrc/ref/cli/)). Two consequences for this requirement. First, (a) is handled: the manifest carries a per-repo `branch`, so `main` here and `master` there is expressible, and `release/*` can be written as an explicit branch per repo (no glob). Second, (c) is handled defensively: a dirty repo on the wrong branch is left alone rather than switched. However the default behaviour *checks out* the manifest branch on a clean repo — which is precisely the "moves the human off their branch" behaviour the requirement forbids; `--no-correct-branch` disables the switch, but then the update happens only if the repo is already on the configured branch. (d) — updating a non-checked-out branch — is not supported: tsrc updates the checked-out branch. Source settles the FF question: the syncer runs `["fetch", "--tags", "--prune", remote.name]` followed by `["merge", "--ff-only", "@{upstream}"]`, and a failed fast-forward raises "updating branch failed" for that repo ([tsrc/syncer.py](https://github.com/your-tools/tsrc/blob/main/tsrc/syncer.py)) — so (b) is **yes, FF-only by design**. Dirty detection uses `get_git_status(...).dirty`; a dirty repo that needs a checkout raises "git repo is dirty: cannot checkout: {branch}" and a dirty repo pinned to a ref raises "git repo is dirty: cannot sync to ref" ([tsrc/syncer.py](https://github.com/your-tools/tsrc/blob/main/tsrc/syncer.py)). Two caveats: manifests that pin a `sha1`/`tag` are applied with `["reset", "--hard", ref]` — never use pinned refs on a checkout a human works in — and with `--no-correct-branch` a repo on the wrong branch raises `IncorrectBranch` rather than being quietly skipped, so in unattended use every repo where the human is on a feature branch shows up as an error ([tsrc/syncer.py](https://github.com/your-tools/tsrc/blob/main/tsrc/syncer.py)). Errors are collected per repo in `Outcome` objects and processing continues to the other repos; the overall exit code on partial failure is **not verified** from the syncer alone. `tsrc foreach` runs a command in every repo and "report[s] failures at the end" rather than aborting on the first failure ([tsrc CLI reference](https://your-tools.github.io/tsrc/ref/cli/)). Verdict: (a) yes via manifest, (b) yes (`merge --ff-only`, per source), (c) yes for a dirty tree (refuses rather than touches), but a *clean* tree on another branch gets switched unless `--no-correct-branch`, which then errors instead of skipping, (d) no.

**vcstool.** Source confirms the README's silence: the git client's `pull` method runs a bare `git pull` — `cmd = [GitClient._executable, 'pull']` with no `--ff-only` and no `--rebase` ([vcstool/clients/git.py](https://github.com/dirk-thomas/vcstool/blob/master/vcstool/clients/git.py)). If the pull fails and `rev-parse --abbrev-ref HEAD` returns `HEAD` (detached), the client **returns returncode 0** while keeping the error text, so a detached checkout is silently reported as success ([vcstool/clients/git.py](https://github.com/dirk-thomas/vcstool/blob/master/vcstool/clients/git.py)). `vcs import` onto an existing directory fetches the remote and runs `git checkout <version> --` — with **no dirty-tree check anywhere in the class** ("no `status --porcelain` or `is_dirty`"), and with `--force` it `rmtree()`s a directory whose remote URL differs from the manifest ([vcstool/clients/git.py](https://github.com/dirk-thomas/vcstool/blob/master/vcstool/clients/git.py)). Mapping: (a) only via a `.repos` manifest `version:` per repo, and only through `import`, which checks out that version (moves the human's HEAD); (b) no — plain `git pull`; (c) no guard; (d) no. Verdict: ruled out for the update role; still a fine `vcs custom --args fetch --prune` parallel fetcher if all you want is the network step.

## 3. Parallelism, speed, and failure reporting

**Why this section matters.** Unattended runs need three things from the runner: concurrency so 20-50 repos refresh in seconds not minutes, a non-zero exit code when *any* repo failed so a cron/launchd job or remote trigger can tell success from failure, and a per-repo summary (ideally machine-readable) so an AI consumer can tell *which* checkout is stale. Findings per tool follow; the mani command-reference page at `manicli.com/commands/exec` returned HTTP 404 during this pass, so mani's flag details below come from the GitHub README and releases page instead.

### 3.1 Per-tool notes (running list)

**mani.** `mani exec` and `mani run` share the runner flags: `--parallel` runs the task concurrently across projects, `--forks` caps concurrency at 4 by default ("maximum number of concurrent processes"), `--ignore-errors` means "continue execution despite errors", `--dry-run` prints without executing, `--ignore-non-existing` skips projects whose path is missing, and project selection is `--all`, `--tags`, `--paths`, or `--target` ([mani docs/commands.md](https://github.com/alajmo/mani/blob/main/docs/commands.md)). Output formats are `--output stream|table|markdown|html` — **no JSON**, so a machine consumer has to parse the table or markdown, or run the task with `--output stream` and structure the output itself ([mani docs/commands.md](https://github.com/alajmo/mani/blob/main/docs/commands.md)). Source (read 2026-09-07) settles the default and the exit code. In `core/exec/text.go`, each command in a project is followed by `if err != nil && !task.SpecData.IgnoreErrors { return err }`, so without `--ignore-errors` the first failing command ends that project's task and returns the error; with `--ignore-errors` the error is dropped and the worker returns `nil` ([core/exec/text.go](https://raw.githubusercontent.com/alajmo/mani/main/core/exec/text.go)). In parallel mode the workers are goroutines under `core.NewSizedWaitGroup(task.SpecData.Forks)` and the outer `Text()` calls `wg.Wait()`, so projects already dispatched run to completion — "stop on first failure" applies within a project, not across the fleet ([core/exec/text.go](https://raw.githubusercontent.com/alajmo/mani/main/core/exec/text.go)). `cmd/exec.go` then does `err = target.Run(...); core.CheckIfError(err)` ([cmd/exec.go](https://raw.githubusercontent.com/alajmo/mani/main/cmd/exec.go)), and `CheckIfError` prints `error: <msg>` to stderr and calls **`os.Exit(1)`** for every non-nil error ([core/errors.go](https://raw.githubusercontent.com/alajmo/mani/main/core/errors.go)). **Net: a failing project exits 1 without `--ignore-errors` and 0 with it** — the flag trades the exit signal for completeness, so an unattended job that wants both must run without the flag and accept that the remaining commands in the failing project are skipped. One caveat: the excerpt did not show how an error raised inside a parallel goroutine is surfaced to `Run()`, so the exit-1 path is confirmed for serial runs and inferred for `--parallel`. `mani sync` has its own `--parallel`/`--forks 4`, `--sync-remotes` ("update git remote state" — remote *configuration*, not fetching commits), and `--status` (display only) ([mani docs/commands.md](https://github.com/alajmo/mani/blob/main/docs/commands.md)).

**myrepos (mr).** The man page URL `myrepos.branchable.com/mr/` returned HTTP 404 in the first pass; the Debian-hosted man page (version 1.20180726) was read on 2026-09-07 and settles the open points. Parallelism: `-j [number]` — "Run the specified number of jobs in parallel, or an unlimited number of jobs with no number specified. This can greatly speed up operations such as updates." ([mr(1) man page](https://manpages.debian.org/unstable/myrepos/mr.1.en.html)). Exit status: **"mr returns nonzero if a command failed in any of the repositories."** — making mr the only tool in this inventory whose non-zero-on-partial-failure behaviour is *documented*, not just inferred from source ([mr(1) man page](https://manpages.debian.org/unstable/myrepos/mr.1.en.html)). `update` is described as "Updates each repository from its configured remote repository. If a repository isn't checked out yet, it will first check it out." Quiet mode `-q` suppresses mr's own output and command output "(including stderr output). If a command fails, the output will be shown." — so a cron log stays empty on success and shows only the failing repo's output, which is the right shape for unattended runs. The offline queue is `~/.mrlog`: "commands that mr has remembered to run later, due to being offline ... If the file is present, mr assumes it is in offline mode." `-f` forces action on repos "that would normally be skipped due to their configuration" ([mr(1) man page](https://manpages.debian.org/unstable/myrepos/mr.1.en.html)). The end-of-run summary line format ("finished (N ok; M failed)") was not quoted by the man page and remains an observation from practice rather than a documented contract.

**gitup.** The README documents behaviour, not plumbing: "gitup will fetch all remotes in a repository" then "will try to fast-forward all branches that have upstreams configured" and "will always skip branches where this is not possible (e.g. dirty working directory or a merge/rebase is required)"; by default it keeps stale remote-tracking branches unless `--prune`/`-p` is given ([README](https://raw.githubusercontent.com/earwig/git-repo-updater/main/README.md)). Flags confirmed: `-c`/`--current-only` (fetch only the current branch's remote), `-f`/`--fetch-only`, `-p`/`--prune`, `-t`/`--depth` (recursion depth when scanning directories), `--add`/`--delete`/`--list` for bookmarks ([README](https://raw.githubusercontent.com/earwig/git-repo-updater/main/README.md)). Three gaps matter for this requirement; two are now settled from source (2026-09-07 pass): (1) **serial** — `update_bookmarks()` and `update_directories()` iterate repos in plain `for` loops with no threads, multiprocessing, or asyncio, so for 20-50 repos the run time is the sum of every fetch, one after another ([src/gitup/update.py](https://raw.githubusercontent.com/earwig/git-repo-updater/main/src/gitup/update.py)); (2) exit code — the update module never calls `sys.exit` and its entry functions return `None`; a fetch error (`GitCommandError`) is printed and the repo is abandoned with a bare `return`, and a branch skip is printed and the loop continues ([src/gitup/update.py](https://raw.githubusercontent.com/earwig/git-repo-updater/main/src/gitup/update.py)), and the CLI wrapper does no accounting either — `src/gitup/__main__.py` just calls `gitup.cli.run()`, and `cli.py`'s `main()` calls `update_bookmarks()` / `update_directories()` / `run_command()` without capturing their (`None`) return values and contains no `sys.exit`; `run()` only wraps `main()` in a `KeyboardInterrupt` handler ([src/gitup/cli.py](https://raw.githubusercontent.com/earwig/git-repo-updater/main/src/gitup/cli.py), [src/gitup/__main__.py](https://raw.githubusercontent.com/earwig/git-repo-updater/main/src/gitup/__main__.py)). **Conclusion: gitup exits 0 on a skipped branch and on an unreachable remote**; only an uncaught Python exception produces a non-zero status. A scheduler cannot rely on `$?`, it has to grep the output for `error:` / `skipped:` lines; (3) no JSON or machine-readable summary flag exists, only human-readable per-branch lines. In other words gitup has the right *semantics* and the weakest *reporting* of the shortlist.

**gita.** Source shows an unbounded fan-out: `exec_async_tasks` does `asyncio.run(_gather_tasks(tasks))` with **no semaphore**, so `gita fetch` on 40 repos spawns 40 `git fetch` processes at once — fast, but it will trip GitLab/GitHub connection throttling or SSH `MaxSessions` limits on large sets ([gita/utils.py](https://github.com/nosarthur/gita/blob/master/gita/utils.py)). Failures do not stop the run: each task prints its output and `if process.returncode != 0: return path`, so the runner returns a list of failed repo paths and continues with the rest ([gita/utils.py](https://github.com/nosarthur/gita/blob/master/gita/utils.py)). `__main__.py` (read 2026-09-07) settles it: `f_git_cmd()` — which `fetch`, `pull`, `super` and `shell` all route through — does `errors = utils.exec_async_tasks(...)` and then `for path in errors: if path: print(path); subprocess.run(args.cmd, cwd=path)`, i.e. it prints each failed repo path and **re-runs the same git command synchronously in that repo**, and the re-run's return code is not checked either; the only `sys.exit` calls in the module are `sys.exit(1)` for a group-name/repo-name clash and `sys.exit(2)` for "Missing commands" in `super`/`shell` ([gita/__main__.py](https://raw.githubusercontent.com/nosarthur/gita/master/gita/__main__.py)). **Conclusion: a failed repo in `gita fetch`/`gita pull` exits 0.** The synchronous re-run is a second hazard for unattended use: the async pass runs with captured output, so a repo that failed because git wanted a password is re-run in the foreground where the prompt can block — `GIT_TERMINAL_PROMPT=0` (section 4.1) is therefore mandatory, not optional, with gita. The parallel status view (`gita ll`) uses a thread pool of `min(cpu_count, len(repos))` ([gita/utils.py](https://github.com/nosarthur/gita/blob/master/gita/utils.py)). No JSON output flag; the `ll` table is the only summary.

**tsrc.** From the syncer source read for section 2: per-repo work is a `Task` handed to an executor with a `parallel` flag; each repo returns an `Outcome` with error/summary fields and processing continues past failures, and the CLI reference says `tsrc foreach` "report[s] failures at the end" ([tsrc/syncer.py](https://github.com/your-tools/tsrc/blob/main/tsrc/syncer.py), [tsrc CLI reference](https://your-tools.github.io/tsrc/ref/cli/)). The `-j/--jobs` count and the final exit code are **not verified** in this pass.

**vcstool.** Parallel by default ("Parallelizes across CPU cores"), `--workers 1` for serial, and it drops to one worker automatically for SSH imports that may need host-key confirmation ([README](https://github.com/dirk-thomas/vcstool)). Per-repo output is grouped under a `=== path (git) ===` header; the detached-HEAD masking noted in section 2 (returncode forced to 0) means its exit status under-reports failures ([vcstool/clients/git.py](https://github.com/dirk-thomas/vcstool/blob/master/vcstool/clients/git.py)). No JSON output.

**ghorg / all-repos / git-xargs (forge bulk family).** ghorg `--concurrency` defaults to 25 ([README](https://github.com/gabrie30/ghorg)); all-repos `--jobs` defaults to 8 with `0`/`-1` meaning CPU count ([README](https://github.com/asottile/all-repos)); git-xargs `--max-concurrent-clones` defaults to 4 ([README](https://github.com/gruntwork-io/git-xargs)). These are clone-throughput knobs; none of the three exposes a per-repo update report suited to an AI consumer, and section 2 already rules them out on semantics.

**mu-repo.** Serial vs parallel is a persisted setting (`mu set-var serial=0|1` or `MU_REPO_SERIAL`) rather than a per-run flag ([mu-repo commands](https://fabioz.github.io/mu-repo/commands/)). Exit-code and summary behaviour **not verified**.

## 4. Unattended and remote fit

**Why this section matters.** The job will run from launchd/cron or from an SSH-triggered command with no human at the keyboard. That imposes four checks on each tool: (1) it must never block on a prompt (password, host-key confirmation, "continue? y/n", TUI), (2) credentials must be reachable from a non-login shell, (3) it needs no daemon or GUI, (4) it should be a single command the remote trigger can call. Forge credential handling is largely git's concern, not the multi-repo tool's — every tool in the set shells out to git — so the credential findings apply uniformly. The GitLab CLI docs page for `glab auth git-credential` rendered only a JavaScript "Loading" shell when fetched (GitLab's file viewer is client-rendered), so that claim is sourced below from the raw file instead.

### 4.1 Credential and prompt handling (applies to all tools)

The `glab auth git-credential` documentation was eventually read from the legacy upstream repo (2026-09-07 pass; the gitlab.com raw path 404'd and docs.gitlab.com redirected to a login endpoint): it confirms the command exists and "Implements git credential helper manager" but contains no configuration example ([git-credential.rst](https://raw.githubusercontent.com/profclems/glab/trunk/docs/source/auth/git-credential.rst)), so the exact `git config` line below remains **not verified** from a primary source — see section 6.4 for the full trail. What *is* structural and tool-independent:

- **SSH remotes** are the lowest-friction unattended path: no token expiry, and every tool in the inventory just runs `git fetch`, which uses whatever `ssh` finds. The catch on macOS is that a launchd/cron job does not inherit the login session's `SSH_AUTH_SOCK`, so a passphrase-protected key will hang the job; either use a key without a passphrase restricted to read-only deploy-key scope, or point `SSH_AUTH_SOCK` at the user's agent socket explicitly in the job environment. Also set `GIT_SSH_COMMAND="ssh -o BatchMode=yes -o StrictHostKeyChecking=accept-new"` so a missing host key fails fast instead of prompting. (These are git/ssh semantics, not claims about any multi-repo tool; vcstool's README independently acknowledges the same hazard by dropping to one worker "for SSH Git imports when host verification is needed" ([README](https://github.com/dirk-thomas/vcstool)).)
- **HTTPS remotes** need a credential helper that answers without a TTY. On macOS git's default `osxkeychain` helper works from launchd as long as the job runs in the user's login context (Keychain is per-user and unlocked at login); `glab auth git-credential` and `gh auth git-credential` are both designed as helpers for exactly this — configure with `git config --global credential.https://gitlab.example.com.helper '!glab auth git-credential'` (exact glab line **not verified** from a primary source after six attempts in the 2026-09-07 pass — the command's own doc page only says "Implements git credential helper manager" with synopsis `glab auth git-credential [flags]` ([git-credential.rst](https://raw.githubusercontent.com/profclems/glab/trunk/docs/source/auth/git-credential.rst)), and the line above is git's generic `!<command>` helper syntax; `glab auth login` offers to write the config for you ([login.go](https://raw.githubusercontent.com/profclems/glab/trunk/commands/auth/login/login.go)), so the safest path is to accept that offer once and copy what it wrote; `gh`'s equivalent `gh auth setup-git` is documented by GitHub). See section 6.4. Set `GIT_TERMINAL_PROMPT=0` in the job so a missing credential fails instead of blocking.
- **Tool-level prompts.** gitbatch is TUI-only ([README](https://github.com/isacikgoz/gitbatch)); git-bulk's `-g` flag asks for confirmation per execution and must be left off ([git-bulk man page](https://github.com/tj/git-extras/blob/main/man/git-bulk.md)); gita disables async for `log`, `difftool`, `mergetool` because they need input — `fetch`/`pull`/`super` do not ([README](https://github.com/nosarthur/gita)); mu-repo's `mu upd` opens WinMerge/meld and is therefore interactive by design ([mu-repo commands](https://fabioz.github.io/mu-repo/commands/)); Google repo's `sync` can stop mid-rebase on conflict and wait for a human `git rebase --continue` ([AOSP repo reference](https://source.android.com/docs/setup/reference/repo)).

### 4.2 Scheduling on macOS (tool-independent)

None of the inventoried tools ships a daemon, scheduler, or HTTP/API mode — every one is a one-shot CLI, which is the right shape: the scheduler and the remote trigger are external and the tool is just the command they call. On macOS the native scheduler is launchd. A **LaunchAgent** in `~/Library/LaunchAgents` runs "on behalf of the logged in user" — which is what you want, because the user's Keychain and SSH agent are only available in that context — whereas a LaunchDaemon runs as root at boot ([launchd.info](https://www.launchd.info/)). The relevant plist keys are `StartInterval` (every *n* seconds), `StartCalendarInterval` (cron-like schedule), `WatchPaths` (fire when a file changes — a cheap local trigger: a remote `ssh host touch ~/.sync-now` fires the job without needing the remote to know the command), `EnvironmentVariables` (where `SSH_AUTH_SOCK`, `GIT_TERMINAL_PROMPT=0`, and `PATH` for a `pipx`/Homebrew install go), and `StandardOutPath`/`StandardErrorPath` for logs ([launchd.info](https://www.launchd.info/)). Load with `launchctl bootstrap gui/$(id -u) <plist>` and fire on demand with `launchctl kickstart gui/$(id -u)/<label>` ([launchd.info](https://www.launchd.info/)). Whether classic `cron` is still supported on current macOS is **not verified** from this source; launchd is the documented path regardless. Note for the other agent designing remote triggering: `launchctl kickstart` over SSH is a complete trigger mechanism with zero new services.

## 5. Fit scoring and shortlist

### 5.1 Scoring method

Six criteria, each scored 0-2 from the evidence in sections 1-4 (2 = built in and documented, 1 = achievable with a one-line git command the tool passes through or a documented flag, 0 = impossible, destructive, or the tool is out of scope). "?" counts as 0 in the total and is flagged, so unverified behaviour lowers a score rather than inflating it. The criteria mirror the requirement statement:

- **C1 Branch selection** — updates `main`/`master`/`release*` per repo, not "whatever is checked out".
- **C2 FF-only** — never merges or rebases.
- **C3 Dirty-safe** — never touches uncommitted work, never switches the human's branch.
- **C4 Off-branch update** — refreshes `main` while a feature branch is checked out.
- **C5 Unattended** — no prompts, no TUI, no daemon, single command (section 4).
- **C6 Reporting** — continues past failures, exit code and per-repo summary usable by a scheduler/agent (section 3).
- **M Maintenance** — recorded separately, not scored, because a dormant tool with the right semantics (myrepos) may still beat an active one with the wrong semantics (ghorg).

### 5.3 Shortlist — worth a local trial

**1. gitup (git-repo-updater) — try first.** It is the only tool whose *default* behaviour is the requirement: fetch all remotes, fast-forward every branch that has an upstream, skip anything dirty or diverged, never merge or rebase ([README](https://github.com/earwig/git-repo-updater)). That covers C2, C3 and C4 without configuration, and C1 is satisfied as a superset (feature branches with upstreams are also fast-forwarded, which cannot lose commits). Its bookmarks (`gitup --add ~/repos/x`, then bare `gitup`) are the "fixed set of local directories" the developer has. The three points that were open in the first pass are now settled from source (2026-09-07): the exit code is 0 when a branch is skipped **and** when a remote is unreachable (the error is printed and swallowed; no `sys.exit` anywhere in `update.py`, `cli.py`, `__main__.py`), and repos are processed serially in a plain `for` loop ([update.py](https://raw.githubusercontent.com/earwig/git-repo-updater/main/src/gitup/update.py), [cli.py](https://raw.githubusercontent.com/earwig/git-repo-updater/main/src/gitup/cli.py)). Two practical consequences: a scheduler must parse stdout for `error:` / `skipped:` lines rather than trust `$?`, and 40 repos over a slow VPN will take the sum of all fetch times — acceptable for a scheduled job, less so for an on-demand trigger. The local trial can therefore focus on timing alone. Install: `brew install gitup` ([README](https://github.com/earwig/git-repo-updater)).

**2. gita — try second, as the runner if gitup's reporting or speed disappoints.** gita gives the registry (`gita add -r`), grouping, a live dirty/ahead/behind view (`gita ll`), and an unbounded-parallel fan-out ([README](https://github.com/nosarthur/gita), [gita/utils.py](https://github.com/nosarthur/gita/blob/master/gita/utils.py)), and it had a release in November 2025 ([PyPI](https://pypi.org/project/gita/)). It does *not* supply the branch logic; the safe incantation is a `cmds.json` entry or `gita super <group> fetch --prune origin main:main master:master` — `git fetch <remote> <src>:<dst>` is FF-only by default for non-checked-out branches and refuses to update the checked-out one, which is exactly the desired failure mode. Pair it with `gita ll` for the per-repo summary. The unbounded concurrency should be watched on large sets.

**3. mani — try third, if a declarative manifest with named tasks is preferred over gita's registry.** mani is the most actively maintained tool in the field (v0.32.1, May 2026), `mani init` scans for existing `.git` directories, and `mani run <task> --all --parallel --forks N --ignore-errors` gives bounded concurrency and per-project table output ([README](https://github.com/alajmo/mani), [docs/commands.md](https://github.com/alajmo/mani/blob/main/docs/commands.md), [releases](https://github.com/alajmo/mani/releases)). Like gita it hosts your git one-liner rather than replacing it. Its worktree support (v0.32.0) is a bonus if the AI consumers are ever moved onto dedicated read-only worktrees of `main`.

**Honourable mention — myrepos.** Semantically it can do everything (per-repo `update =` override, `-j`, offline retry queue) ([myrepos](https://myrepos.branchable.com/)), and it is the only tool here whose man page *documents* a non-zero exit when any repository's command fails ([mr(1)](https://manpages.debian.org/unstable/myrepos/mr.1.en.html)) — which lifts its C6 score to 2 and its total to 8, ahead of mani and tsrc on paper. It still has had no release since 2018-07-26, so the trade is a reliable exit contract against a dormant upstream; choose it if it is already installed and trusted, or if the exit code matters more than active maintenance.

### 5.4 Ruled out, and why

- **ghorg** — `git pull` then `git clean` on existing directories; "All local changes in the cloned directory by default will be overwritten" ([README](https://github.com/gabrie30/ghorg)). Fails C3 destructively; `--branch` is global so it also fails C1. Keep it for *bootstrapping* a GitLab group's clones, not for refreshing them.
- **git-xargs** — clones fresh into `/tmp` and opens PRs; GitHub-only; never operates on existing checkouts ([README](https://github.com/gruntwork-io/git-xargs)).
- **all-repos** — manages its own `output_dir` mirror set, default branch only; it is for org-wide code changes, not for the human's working checkouts ([README](https://github.com/asottile/all-repos)).
- **vcstool** — bare `git pull` with no dirty check and a detached-HEAD failure masked as success; `import --force` deletes directories ([vcstool/clients/git.py](https://github.com/dirk-thomas/vcstool/blob/master/vcstool/clients/git.py)).
- **Google repo** — `repo sync` rebases the checked-out branch and can park on conflicts ([AOSP repo reference](https://source.android.com/docs/setup/reference/repo)); rewrite-by-design contradicts FF-only.
- **tsrc** — the closest near-miss: FF-only and dirty-refusing by source ([tsrc/syncer.py](https://github.com/your-tools/tsrc/blob/main/tsrc/syncer.py)), but it updates only the checked-out branch and either switches a clean tree off the human's branch or errors on it, so it cannot refresh `main` while someone works on a feature branch (C4 = 0). Reconsider only if the checkouts are dedicated agent-owned clones that always sit on `main`.
- **gitbatch** — TUI only, no headless mode ([README](https://github.com/isacikgoz/gitbatch)).
- **mu-repo, git-bulk** — pure pass-throughs with no dirty guard and no verified failure reporting; gita and mani do the same job with better upkeep or better output.
- **meta, gr, gws, west, mgit** — not verified in this pass; all are manifest-owned or Node-dependent and none was cited by the landscape sources as having FF-only/dirty-safe semantics, so they were not promoted over the shortlist.
