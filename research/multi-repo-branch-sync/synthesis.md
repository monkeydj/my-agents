## Executive Summary

- **No off-the-shelf multi-repo CLI meets the requirement as shipped.** Of 18 tools inventoried, only gitup (git-repo-updater) has the right default semantics — fetch all remotes, fast-forward every upstream-tracking branch, skip dirty or diverged branches, never merge or rebase ([gitup README](https://github.com/earwig/git-repo-updater)) — and it scores 10/12 versus 7/12 for the next tier (mani, myrepos, tsrc); but its source shows it runs repos serially and never calls `sys.exit`, so it exits 0 even on a skip or an unreachable remote, and it has no machine-readable output ([existing-cli-tools.md sec. 6.1](https://github.com/earwig/git-repo-updater)); it cannot be wired into a scheduler or an agent hand-off without a wrapper around it.
- **Hand-roll a zsh script (`repo-sync`) over git primitives; do not adopt gitup or wrap gita/mani.** Every per-repo step is a documented one-liner — `git fetch --prune --atomic`, `git fetch origin b:b` for non-checked-out branches, `git merge --ff-only` for the checked-out one ([git-fetch(1)](https://git-scm.com/docs/git-fetch), [git-merge(1)](https://git-scm.com/docs/git-merge)) — and the value the tools do not supply (run lock, reader-safe publish, machine-readable status, exit-code contract) is exactly what a 300-line script owns.
- **The human's checkout is refreshed by policy "skip when dirty"; agents never read it.** The wrapper fast-forwards non-checked-out branches always, the checked-out branch only when the tree is quiescent, and stashing is opt-in only, because `stash --include-untracked` deletes untracked files via `git clean` and a conflicting `pop` "is not removed from the stash list" ([git-stash(1)](https://git-scm.com/docs/git-stash)). Agents read detached snapshot worktrees behind a symlink that is flipped with one `rename(2)`, the pattern kubernetes/git-sync uses because "git checkouts are not 'atomic' operations" ([kubernetes/git-sync README](https://github.com/kubernetes/git-sync/blob/master/README.md), [rename(2)](https://keith.github.io/xcode-man-pages/rename.2.html)).
- **Trigger stack: `~/Library/LaunchAgents` on `StartCalendarInterval` every 30 minutes, plus an SSH forced command (`restrict,command=`) for the remote trigger; webhooks and Claude Code scheduling are out.** `StartCalendarInterval` catches up after sleep where `StartInterval` and cron silently skip ([launchd.plist(5)](https://keith.github.io/xcode-man-pages/launchd.plist.5.html)); GitLab permanently disables a webhook "after 40 consecutive failures" so a sleeping laptop cannot host one ([GitLab Docs, Webhooks](https://docs.gitlab.com/user/project/integrations/webhooks/)); routines run in the cloud and cannot touch `~/Documents` ([Anthropic, Introducing routines](https://claude.com/blog/introducing-routines-in-claude-code)).
- **Hand-off to codebase-memory-mcp is one rename-replaced JSON file, `refresh.json`, with an explicit `project` name per branch.** `index_repository` derives the project name from `repo_path`, so a symlink named `main` would collide every repo into one project; the contract carries `project = <repo>@<branch>`, `commit`/`previous_commit` for `detect_changes --since`, and `run.state` so an agent never indexes mid-run ([remote-and-agent-facing.md sec. 3.4]).
- **Unattended credential is a passphrase-less read-only deploy key injected via `GIT_SSH_COMMAND` only inside the wrapper, never into the human's git config.** `IdentitiesOnly=yes -o IdentityAgent=none -o BatchMode=yes` makes the run identical with or without a login session and fails fast instead of holding the lock on a prompt ([git(1) GIT_SSH_COMMAND](https://git-scm.com/docs/git#Documentation/git.txt-codeGITSSHCOMMANDcode), [GitLab Docs, Deploy keys](https://docs.gitlab.com/user/project/deploy_keys/)); the login keychain is unavailable to a LaunchDaemon or a night-time SSH trigger ([security(1)](https://keith.github.io/xcode-man-pages/security.1.html)).

## Decision: adopt, wrap, or hand-roll

### What the existing-tool survey rules out (source: `existing-cli-tools.md`)

The survey scored 13 tools against six criteria: C1 per-repo branch selection, C2 FF-only, C3 dirty-safe, C4 update a non-checked-out branch, C5 unattended, C6 reporting (exit code + per-repo summary). The findings that constrain the decision:

- **Adopting a tool unmodified is not viable.** Every tool in the runner family except gitup only runs `git pull` on whatever branch is checked out, which fails branch selection, dirty safety, and off-branch update by construction ([existing-cli-tools.md sec. 2]). gitup is the sole exception: it fast-forwards "all branches that have upstreams configured" and "will always skip branches where this is not possible (e.g. dirty working directory or a merge/rebase is required)" ([gitup README](https://raw.githubusercontent.com/earwig/git-repo-updater/main/README.md)). Its gaps are operational, not semantic, and the verification pass confirmed them from source (`src/gitup/update.py`): repos are processed serially, fetch errors are printed and swallowed, and there is no `sys.exit` anywhere, so the process exits 0 on skip and on an unreachable remote; there is no JSON summary ([existing-cli-tools.md sec. 6.1](https://github.com/earwig/git-repo-updater)).
- **Several popular tools are actively unsafe for a human's working checkout.** ghorg runs `git pull` then `git clean` on an existing directory — "All local changes in the cloned directory by default will be overwritten" ([ghorg README](https://github.com/gabrie30/ghorg)). vcstool runs bare `git pull` with no dirty check anywhere in its git client and forces returncode 0 on a detached-HEAD failure ([vcstool/clients/git.py](https://github.com/dirk-thomas/vcstool/blob/master/vcstool/clients/git.py)). Google `repo sync` rebases the checked-out branch and parks on conflicts ([AOSP repo reference](https://source.android.com/docs/setup/reference/repo)). tsrc is FF-only by source (`merge --ff-only @{upstream}`) and refuses dirty trees, but it checks out the manifest branch on a clean tree or errors on it, so it cannot refresh `main` while a feature branch is checked out ([tsrc/syncer.py](https://github.com/your-tools/tsrc/blob/main/tsrc/syncer.py)).
- **The runners that remain (gita, mani, myrepos) are loops, not solutions.** gita's `super`/`cmds.json` and mani's `run <task>` pass an arbitrary git command to every registered repo, so the FF-only branch logic is still yours to write; gita fans out with an unbounded asyncio gather (no semaphore) and returns a list of failed paths with no `sys.exit` tied to it, so it likely exits 0 on partial failure ([gita/utils.py](https://github.com/nosarthur/gita/blob/master/gita/utils.py)); mani caps concurrency with `--forks` (default 4) and needs `--ignore-errors` to continue past a failing project, and offers table/markdown/html output but no JSON ([mani docs/commands.md](https://github.com/alajmo/mani/blob/main/docs/commands.md)); myrepos has had no release since 2018-07-26 ([myrepos](https://myrepos.branchable.com/)).
- **A trustworthy non-zero exit on partial failure is documented for exactly one tool, myrepos** ("mr returns nonzero if a command failed in any of the repositories", [mr(1)](https://manpages.debian.org/unstable/myrepos/mr.1.en.html)); mani exits 1 via `os.Exit(1)` unless `--ignore-errors`, gitup and gita exit 0 on partial failure ([existing-cli-tools.md sec. 6]). For an unattended job that an agent polls, that is the single most important property, and it has to be tested by fault injection regardless of which tool is chosen.
- **The safe git incantation the survey converged on** is `git fetch --prune origin main:main master:master` — a refspec fetch into a non-checked-out branch is FF-only by default and git refuses to update the currently checked-out branch, "which is exactly the desired failure mode" ([existing-cli-tools.md sec. 5.3, gita entry](https://github.com/nosarthur/gita)). This is a one-liner that any runner can host and that a hand-rolled function can own outright.

### Verdict: hand-roll, pure zsh over git, with `git maintenance` as the only adopted tool

**Not adopt.** gitup is the closest fit (10/12) but three things disqualify it as the agent-facing engine, all now confirmed from its source: it exits 0 on skip and on an unreachable remote, it has no machine-readable output, and it processes repos serially ([existing-cli-tools.md sec. 6.1](https://github.com/earwig/git-repo-updater)). It also operates only on the human's checkout and has no concept of a reader-safe publish step or a status document, which are two of the three hard requirements.

**Not wrap.** gita and mani would supply only a registry and a parallel loop; the branch logic, dirty classification, lock, publish and status would still be written by hand, and both add a Python or Go runtime plus an undocumented exit-code contract to the remote-trigger path ([gita/utils.py](https://github.com/nosarthur/gita/blob/master/gita/utils.py), [mani docs/commands.md](https://github.com/alajmo/mani/blob/main/docs/commands.md)). Stock zsh already has bounded parallelism (`zargs -P`, exit 123 on partial failure) and a kernel lock (`zsystem flock`) ([zsh Functions/Misc/zargs](https://github.com/zsh-users/zsh/blob/master/Functions/Misc/zargs), [zsh/system module docs](https://github.com/zsh-users/zsh/blob/master/Doc/Zsh/mod_system.yo)), so the wrapper gains nothing from a runner it would have to fence.

**Hand-roll, precisely scoped.** One executable zsh file, `repo-sync`, that (1) refreshes the human's clones with policy A, (2) publishes detached snapshot worktrees behind a `rename(2)` symlink flip for agents, and (3) writes `refresh.json`. The one existing tool it *does* enlist is `git maintenance start --scheduler=launchctl`, whose hourly `prefetch` moves objects into `refs/prefetch/*` in the background so the wrapper's fetch is usually a no-op and the publish window shrinks ([git-maintenance(1)](https://git-scm.com/docs/git-maintenance)). gh/glab are used at discovery and pre-flight only, never in the per-repo loop ([wrapper-over-git.md sec. 6](https://cli.github.com/manual/gh_auth_status)).

**One deliberate deviation from `remote-and-agent-facing.md`**: that file recommends a *separate bare mirror* per repo (layout B+D); this synthesis publishes reader snapshots as linked worktrees of the *human's existing clone* (policy C+D). Reasoning and the migration trigger are in Contradictions item 1.

**Walk-through.** Every entry point runs the same executable and the first thing it does is take a non-blocking kernel lock; a second trigger while a run is live prints the current `refresh.json` and exits 3, so a remote caller can distinguish "already running" from failure ([zsh/system module docs](https://github.com/zsh-users/zsh/blob/master/Doc/Zsh/mod_system.yo), [wrapper-over-git.md sec. 4.4]). Pre-flight pins `PATH`, injects the deploy key through `GIT_SSH_COMMAND` for this process only, disables terminal prompts, parses the manifest, and marks the status document `running` without touching its previous `repos` map ([remote-and-agent-facing.md sec. 3.5]). Repos then run four at a time. In each, one `--atomic --porcelain` fetch is the only network step and never touches the working tree; the porcelain lines give old and new SHAs per ref ([git-fetch(1)](https://git-scm.com/docs/git-fetch)). The human's clone is classified once — porcelain-v2 status plus the git-prompt marker files — and each major branch is moved by the primitive that already carries the right refusal: `fetch b:b` for branches nobody has checked out, `merge --ff-only` for a clean checked-out branch, nothing for a dirty or mid-rebase tree ([git-fetch(1)](https://git-scm.com/docs/git-fetch), [git-merge(1)](https://git-scm.com/docs/git-merge), [git-prompt.sh](https://github.com/git/git/blob/master/contrib/completion/git-prompt.sh)). Publishing is independent of that outcome: for each major branch whose `origin/<b>` moved, a new detached, locked worktree named `<b>@<sha>` is materialised from the human clone's object store and the `<b>` symlink is repointed with one `rename(2)`, so an agent sees the old complete tree or the new complete tree and never a mixture ([git-worktree(1)](https://git-scm.com/docs/git-worktree), [rename(2)](https://keith.github.io/xcode-man-pages/rename.2.html), [mv(1) macOS](https://keith.github.io/xcode-man-pages/mv.1.html)). The parent assembles `summary.tsv`, prunes snapshots past the retention grace, rewrites `refresh.json` as `idle` in one rename, and fires an idempotent hook. Agents read only `refresh.json` and the `<b>` symlink; the decision rule (never indexed → `index_repository`; `changed` → `detect_changes` since the last indexed SHA; otherwise nothing) is what turns the file into a hand-off ([remote-and-agent-facing.md sec. 3.5]).

The primitives below are the building blocks the diagram's "refresh" and "publish" boxes expand to.

### Refresh primitives — every local ref move is a fast-forward or nothing

- **Network step is `git fetch`, which never touches the working tree or index**; it writes only `refs/remotes/<remote>/*` and `FETCH_HEAD` ([git-fetch(1)](https://git-scm.com/docs/git-fetch)). The wrapper's fetch line is `git -C "$repo" fetch --prune --atomic --no-write-fetch-head origin`: `--prune` removes remote-tracking refs for branches deleted on the forge so a reader never sees a dead `release/*`; `--atomic` makes the ref update all-or-nothing per repo ("Either all refs are updated, or on error, no refs are updated") ([git-fetch(1)](https://git-scm.com/docs/git-fetch)). Omit `--prune-tags` because it deletes human-created local tags ([git-fetch(1)](https://git-scm.com/docs/git-fetch)).
- **Never put `+` on a refspec targeting `refs/heads/*`.** The leading `+` (or `--force`) overrides every non-fast-forward rejection ([git-fetch(1) refspec](https://git-scm.com/docs/git-fetch#_refspec_)); the default `+refs/heads/*:refs/remotes/origin/*` is correct only because remote-tracking refs are supposed to mirror the remote. `release*` branches are trackable with one pattern refspec (`'+refs/heads/release*:refs/remotes/origin/release*'`), subject to "exactly one `*` on both sides" ([git-fetch(1)](https://git-scm.com/docs/git-fetch#_refspec_)).
- **Non-checked-out branch: `git fetch origin main:main`.** Git "refuses to update the head which corresponds to the current branch" and rejects non-fast-forwards without `+`, so this one command carries both guards and signals skip via non-zero exit plus a `! [rejected]` line ([git-fetch(1)](https://git-scm.com/docs/git-fetch)). Never pass `--update-head-ok`; it exists "purely for the internal use for `git pull`" ([git-fetch(1)](https://git-scm.com/docs/git-fetch)).
- **Checked-out branch: `git merge --ff-only refs/remotes/origin/<b>`.** "When not possible, refuse to merge and exit with a non-zero status"; pre-merge checks abort when uncommitted changes overlap files the merge would update or when anything is staged ([git-merge(1)](https://git-scm.com/docs/git-merge)). Prefer separate `fetch` + `merge --ff-only` over `pull --ff-only` because the fetch is shared across branches and can run even when the tree is dirty ([wrapper-over-git.md sec. 1.4](https://git-scm.com/docs/git-pull)). `--autostash` is disqualified: "the final stash application after a successful merge might result in non-trivial conflicts" that an unattended job cannot resolve ([git-pull(1)](https://git-scm.com/docs/git-pull)).
- **Neutralise the human's global config on every call**: `git -c pull.rebase=false -c pull.ff=only -c merge.ff=only -c fetch.prune=true ...`, because a user with `pull.rebase=true` in `~/.gitconfig` would otherwise rebase silently ([git-pull(1)](https://git-scm.com/docs/git-pull), [git-config(1) merge.ff](https://git-scm.com/docs/git-config#Documentation/git-config.txt-mergeff)).
- **Plumbing alternative for atomic multi-branch moves**: `git merge-base --is-ancestor old new` (exit 0 iff fast-forward) then `git update-ref refs/heads/b new old` — the three-argument form is a compare-and-swap that refuses if the human committed between read and write; `update-ref --stdin` with `start/prepare/commit` moves several branches all-or-nothing ([git-update-ref(1)](https://git-scm.com/docs/git-update-ref), [git-merge-base(1)](https://git-scm.com/docs/git-merge-base#Documentation/git-merge-base.txt---is-ancestor)). Documented caveat: "a concurrent reader may still see a subset of the modifications" — ref atomicity is not a reader snapshot ([git-update-ref(1)](https://git-scm.com/docs/git-update-ref)). Avoid `git branch -f` in an unattended job: no FF check, no CAS ([git-branch(1)](https://git-scm.com/docs/git-branch#Documentation/git-branch.txt--f)).
- **`git maintenance` prefetch complements, does not replace, the wrapper.** `git maintenance start --scheduler=launchctl` installs an hourly `prefetch` that writes to `refs/prefetch/*` only, so branches never move but the wrapper's own fetch usually has nothing left to download ([git-maintenance(1)](https://git-scm.com/docs/git-maintenance)). `maintenance register` stores paths in the multi-valued global `maintenance.repo`, a candidate single source of truth for the repo list ([git-maintenance(1)](https://git-scm.com/docs/git-maintenance)).
- **Worktrees**: a branch can be checked out in at most one worktree, so a reader worktree must be `--detach`ed to avoid competing with the human's `main` ([git-worktree(1)](https://git-scm.com/docs/git-worktree)). `git worktree add --detach --lock --reason "repo-sync reader" <path> origin/main` creates a locked read-only checkout; `git worktree list --porcelain` reveals which branches are checked out where; `git rev-parse --git-common-dir` yields the shared `.git` for the lock file ([git-worktree(1)](https://git-scm.com/docs/git-worktree)).

### Default-branch detection (per run, no forge API)

Layered lookup: (1) `git symbolic-ref -q --short refs/remotes/origin/HEAD` — microseconds, fails only when `origin/HEAD` was never set or is stale after a rename ([git-symbolic-ref(1)](https://git-scm.com/docs/git-symbolic-ref)); (2) `git remote set-head origin -a` after the fetch — "the remote is queried to determine its `HEAD`" and it "will only work if `refs/remotes/origin/next` already exists; if not it must be fetched first", so ordering is fetch-then-set-head ([git-remote(1)](https://git-scm.com/docs/git-remote#Documentation/git-remote.txt-emset-headem)); (3) `git ls-remote --symref origin HEAD` as a pure query ([git-ls-remote(1)](https://git-scm.com/docs/git-ls-remote#Documentation/git-ls-remote.txt---symref)); (4) `gh repo view --json defaultBranchRef,isArchived` ([gh repo view manual](https://cli.github.com/manual/gh_repo_view)) or `glab api "projects/<url-encoded path>" | jq -r .default_branch` — discovery-time only, since it costs an API call and credentials per repo ([wrapper-over-git.md sec. 2.4](https://gitlab.com/gitlab-org/cli/-/tree/main/docs/source/repo)). Do not parse `git remote show origin`; it is human porcelain ([git-remote(1)](https://git-scm.com/docs/git-remote)).

`release*` enumeration uses `git for-each-ref --sort=-v:refname --format='%(refname:lstrip=3)' 'refs/remotes/origin/release*'`; the `%(upstream:trackshort)` field (`<` behind, `>`/`<>` diverged) and `%(worktreepath)` (which worktree, if any, has the branch checked out) answer "fast-forwardable?" and "checked out anywhere?" in one pass ([git-for-each-ref(1)](https://git-scm.com/docs/git-for-each-ref)). Two policies for local `release*`: **mirror-only** (readers consume `origin/release/*` directly; nothing can diverge — recommended) or **local-tracking** (create and fast-forward `refs/heads/release/*`; only if the human's tooling expects them) ([wrapper-over-git.md sec. 2.3](https://git-scm.com/docs/git-for-each-ref)).

### Dirty-tree classification

`git status --porcelain=v2 --show-stash` is the only status format documented as stable for scripts; headers give `branch.head`, `branch.upstream`, `branch.ab +A -B`, and `stash N`; entry lines `1`/`2` are tracked changes (`XY` with `.` for unchanged), `u` is an unmerged conflict entry (automatic skip), `?` untracked ([git-status(1)](https://git-scm.com/docs/git-status)). Always run it as `git --no-optional-locks status --porcelain=v2 -z --untracked-files=normal --show-stash`, because plain `status` "will automatically refresh the index ... writing out the result" and the resulting `index.lock` can make the human's concurrent `git commit` fail ([git-status(1)](https://git-scm.com/docs/git-status)). Do not pass `--ignored`, or `node_modules/`/`.venv/` make an untouched repo look dirty ([wrapper-over-git.md sec. 3.1](https://git-scm.com/docs/git-status)).

Porcelain v2 has no header for "rebase/merge in progress"; the stable detector is the marker-file test git's own prompt uses — `rebase-merge/`, `rebase-apply/{rebasing,applying}`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `sequencer/todo`, `BISECT_LOG` — resolved under `git rev-parse --absolute-git-dir`, not `"$repo/.git"`, because in a linked worktree `.git` is a file and the markers live in the private worktree dir ([contrib/completion/git-prompt.sh](https://github.com/git/git/blob/master/contrib/completion/git-prompt.sh)). Detached HEAD is not dirty: it means no branch is checked out, so every target branch is free to move via `fetch b:b` ([wrapper-over-git.md sec. 3.2](https://github.com/git/git/blob/master/contrib/completion/git-prompt.sh)).

**Policy verdict: A (skip) + C (script-owned reader worktree); B (stash) is opt-in only.**

| Policy | Human checkout touched | Dirty repo refreshed for agents | Unattended-safe | Extra state |
|---|---|---|---|---|
| A. Skip checked-out branch when dirty; `fetch b:b` everything else | only when clean | refs yes, tree no | yes | none |
| B. `stash push --include-untracked` → `merge --ff-only` → `stash pop --index` | always | yes | **no** | stash entries |
| C. Detached, locked reader worktree per repo, `reset --hard origin/<b>` | never (optional FF when clean) | yes | yes | one worktree per repo/branch |

Why B is disqualified for unattended use: `--include-untracked` means untracked files "are also stashed and then cleaned up with `git clean`", so a SIGKILL or laptop sleep between push and pop leaves the human's new files existing only in `refs/stash`; a conflicting `pop` "is not removed from the stash list. You need to resolve the conflicts by hand", leaving the repo both fast-forwarded and mid-conflict, which the classifier then skips forever ([git-stash(1)](https://git-scm.com/docs/git-stash)). Also `stash push` on a clean tree exits 0 with "No local changes to save", so an unconditional pop would pop the *human's* stash — guard by comparing `git rev-parse -q --verify refs/stash` before and after ([wrapper-over-git.md sec. 3.4](https://git-scm.com/docs/git-stash)). Why untracked-only still counts as dirty under A: a non-colliding untracked file lets the FF through and "the human's diff base silently moves under their feet"; offer `--allow-untracked` as the opt-in ([wrapper-over-git.md sec. 3.3](https://git-scm.com/docs/git-merge)). Why C is the strongest answer: it never writes to a directory the human edits, a detached worktree has no branch to diverge so FF-only is moot and it mirrors the forge exactly (a human's unpublished local commits on `main` correctly stay out of the shared knowledge base), and the object store is shared so the cost is one extra checkout, not a clone ([git-worktree(1)](https://git-scm.com/docs/git-worktree)). Run reader-worktree git with `-c core.hooksPath=/dev/null` so the human's IDE hooks do not fire in the unattended run ([wrapper-over-git.md sec. 3.5](https://git-scm.com/docs/git-worktree)).

### Wrapper shell design (source: `wrapper-over-git.md` sec. 4)

- **Inventory**: scan or forge-enumerate *once* to generate `~/.config/repo-sync/repos` (one absolute path per line, `#` comments, `~` allowed), then always run from the list; validate each entry with `git rev-parse --show-toplevel` before the parallel phase and `sort -u` the result so `~/src/app` and `~/src/app/sub` do not refresh the same repo twice ([wrapper-over-git.md sec. 4.1](https://git-scm.com/docs/git-maintenance)). Scan with `find ~/src -mindepth 2 -maxdepth 3 -name .git -prune -print0` — no `-type d`, because `.git` is a file in worktrees and submodules ([wrapper-over-git.md sec. 4.2](https://git-scm.com/docs/git-worktree)).
- **Parallelism**: fetch is network-bound; start at `REPO_SYNC_JOBS=4`, raise to 8 only if measured. Stock options: `xargs -P N` (exit 1 on any failure, not which), zsh `zargs -P N` (batch-parallel, not sliding; exit 123 if any invocation exited 1-125, matching GNU xargs) ([zsh Functions/Misc/zargs](https://github.com/zsh-users/zsh/blob/master/Functions/Misc/zargs)), or background jobs + `wait` with `$jobstates` polling since macOS `/bin/zsh` 5.9 has no `wait -n` ([bash NEWS](https://tiswww.case.edu/php/chet/bash/NEWS)). GNU `parallel` (`brew install parallel`) gives a sliding window, `--group` output, `--joblog` TSV, and exit = number of failed jobs; detect it and fall back to `zargs` ([wrapper-over-git.md sec. 4.3.4](https://github.com/zsh-users/zsh/blob/master/Functions/Misc/zargs)).
- **Reporting contract**: each repo job writes only `<slug>.log` and an atomically-renamed `<slug>.result` line under `${XDG_STATE_HOME:-~/.local/state}/repo-sync/runs/<UTC-ts>/`; the parent concatenates them into `summary.tsv` and flips a `latest` symlink with `ln -sfn` only after the summary exists. Fixed status vocabulary: `OK`, `UPTODATE`, `SKIPPED`, `DIVERGED`, `FAILED` ([wrapper-over-git.md sec. 4.4]). Exit codes: `0` all good, `1` any `FAILED` (or any `SKIPPED`/`DIVERGED` under `--strict`), `2` usage/config error, `3` global lock held (so a remote trigger can treat it as "retry later"), `124` reserved for `timeout` wrappers ([wrapper-over-git.md sec. 4.4]).
- **Prompt-proofing**: `GIT_TERMINAL_PROMPT=0` and `GIT_SSH_COMMAND='ssh -oBatchMode=yes -oConnectTimeout=10'` inside the per-repo function, not in the user's environment ([wrapper-over-git.md sec. 4.4]).
- **`--dry-run` vs `--fetch-only`**: `--dry-run` uses `git fetch --dry-run` ("Show what would be done, without making any changes"; `FETCH_HEAD` "is never written") and mutates nothing; `--fetch-only` does the real, always-safe fetch and prints the true delta via `%(upstream:trackshort)` ([git-fetch(1)](https://git-scm.com/docs/git-fetch), [git-for-each-ref(1)](https://git-scm.com/docs/git-for-each-ref)). Never use `git config --add` from the wrapper; it duplicates on every run ([wrapper-over-git.md sec. 4.5]).
### Concurrency safety — three actors, three mechanisms (source: `wrapper-over-git.md` sec. 5)

- **Wrapper vs wrapper — run lock.** macOS ships the `flock(2)` syscall but not util-linux `flock(1)`. Ranking for this use case: `zsystem flock` from the `zsh/system` module (kernel `fcntl` lock, released when the shell exits for any reason including SIGKILL; `-t 0` for non-blocking; status 0 ok, 1 fail, 2 timeout) > `/usr/bin/shlock -f lock -p $$` (stock, `link(2)`-atomic, self-cleaning via `kill -0` on the recorded PID) > `mkdir` lock with manual stale-PID check > Homebrew `flock`/procmail ([zsh/system module docs](https://github.com/zsh-users/zsh/blob/master/Doc/Zsh/mod_system.yo), [shlock(1)](https://keith.github.io/xcode-man-pages/shlock.1.html)). Kernel locks win because a `mkdir` lock left behind by a killed job blocks every future run, and PID liveness checks are heuristic since PIDs are reused ([wrapper-over-git.md sec. 5.1]). Caveat: the `fcntl` lock is released if the parent exits while children still run, so the parent must stay alive until `wait` returns ([zsh/system module docs](https://github.com/zsh-users/zsh/blob/master/Doc/Zsh/mod_system.yo)). Per-repo locks go in `$(git rev-parse --git-common-dir)/repo-sync.lock`, so a remote "sync just repo X" can run alongside a sweep ([wrapper-over-git.md sec. 5.2]).
- **Wrapper vs human — git's own locks.** `core.filesRefLockTimeout` retries an individual ref lock for 100 ms by default; `core.packedRefsTimeout` retries `packed-refs` for 1000 ms; `index.lock` has **no retry** and fails immediately with "Another git process seems to be running" ([Documentation/config/core.adoc](https://github.com/git/git/blob/master/Documentation/config/core.adoc)). Rules: never take the index lock without need (`--no-optional-locks status`); treat "cannot lock ref"/"index.lock ... File exists" as `FAILED reason=lock` and let the next run retry rather than loop-retrying inside the job; never delete `index.lock` from the wrapper; every FF lands in the reflog (`core.logAllRefUpdates` is on in non-bare repos), so `git reset --keep main@{1}` undoes it; run wrapper git with `-c core.hooksPath=/dev/null` ([wrapper-over-git.md sec. 5.3](https://github.com/git/git/blob/master/Documentation/config/core.adoc)). Audit rule: any `git` call in the script that is not `fetch`, `for-each-ref`, `rev-parse`, `merge-base`, `update-ref`, `ls-remote`, `symbolic-ref`, or `--no-optional-locks status` can contend with the human and must be justified ([wrapper-over-git.md sec. 5.3]).
- **Wrapper vs reader — the publish step.** `checkout`/`merge --ff-only` rewrite the working tree file by file; git has no working-tree snapshot isolation, so the wrapper must build one ([wrapper-over-git.md sec. 5.4]). Three patterns: (1) lock handshake — exclusive `zsystem flock` on `<reader>/.sync.lock` while mutating, agents take `-r` shared locks; weakest, needs cooperating readers ([zsh/system module docs](https://github.com/zsh-users/zsh/blob/master/Doc/Zsh/mod_system.yo)). (2) **Symlink flip (recommended)** — two detached slots `slot-a`/`slot-b` and a `current` symlink agents open; update the inactive slot, then `ln -sfn slot-a current.tmp && mv -h current.tmp current`. `rename(2)` "guarantees that an instance of new will always exist, even if the system should crash in the middle" ([rename(2)](https://keith.github.io/xcode-man-pages/rename.2.html)); macOS `mv` lacks `-T`, so `-h` ("If the target operand is a symbolic link to a directory, do not follow it") is what stops `mv` from moving the temp link *into* the pointed-to directory ([mv(1) macOS](https://keith.github.io/xcode-man-pages/mv.1.html)). Slots and symlink must share one volume (`EXDEV`, and `mv` silently degrades to copy-and-delete across volumes); use a relative link target ([mv(1) macOS](https://keith.github.io/xcode-man-pages/mv.1.html)). Reader contract: `realpath` the `current` link once per job, then read through the resolved slot; a job stays consistent until the flip *after* the next one, so cadence and max job length must be compatible or a third slot added ([wrapper-over-git.md sec. 5.4.2]). (3) Fresh worktree per run named by SHA, prune older than N — strongest, most disk, path *is* the commit ([git-worktree(1)](https://git-scm.com/docs/git-worktree)). Not covered by any swap: readers that run `git log`/`git show origin/main:path` see refs move individually; record the published SHAs in `current/.repo-sync.json` at swap time so agents read those instead of live refs ([wrapper-over-git.md sec. 5.4.4]).

### Forge CLIs: inventory and pre-flight only, never in the per-repo loop (source: `wrapper-over-git.md` sec. 6)

- **Pre-flight**: `gh auth status --hostname H` "will exit with 1 and output to stderr" on any host problem — but with `--json` it "will always exit with zero regardless of any authentication issues", so parse instead of trusting the code ([gh auth status](https://cli.github.com/manual/gh_auth_status)). `glab auth status --hostname H` plays the same role for GitLab (wording not verified; docs page unrenderable) ([wrapper-over-git.md sec. 6.1]). Map pre-flight failure to wrapper exit 2 — nothing touched. SSH-only estates can substitute `git ls-remote --exit-code <repo> HEAD` ([git-ls-remote(1)](https://git-scm.com/docs/git-ls-remote#Documentation/git-ls-remote.txt---symref)).
- **Headless HTTPS credential**: `gh auth setup-git` once registers gh as git's credential helper; or feed `gh auth token --hostname H` through a `GIT_ASKPASS` script so the token never hits argv, a file, or the log ([gh auth token](https://cli.github.com/manual/gh_auth_token)).
- **Discovery** (regenerates `discovered.tsv`, reconciled against `repos` by report, not action): `gh repo list ORG --limit 1000 --no-archived --source --json nameWithOwner,defaultBranchRef,sshUrl` — the `--limit` default is **30** and silently truncates ([gh repo list](https://cli.github.com/manual/gh_repo_list)); `glab repo list -g GROUP -G --archived=false -P 100 -p N -F json` — `-G/--include-subgroups` defaults to false (the subgroup trap), pages cap at 100, and glab does not auto-paginate ([glab docs/source/repo/list.md](https://gitlab.com/gitlab-org/cli/-/blob/main/docs/source/repo/list.md)); or `glab api --paginate "groups/<%2F-encoded>/projects?include_subgroups=true&archived=false&simple=true&per_page=100"` with `default_branch // "main"` because it is null for empty projects ([wrapper-over-git.md sec. 6.3]). Mirror `path_with_namespace` as the on-disk layout (`~/src/group/subgroup/project`) so the inventory is deterministic; flag `ssh_url_to_repo` drift as `RENAMED` and `remote set-url` it ([wrapper-over-git.md sec. 6.3]).
- **Rate limits are irrelevant if forge calls stay out of the sweep**: GitHub authenticated primary is "5,000 requests per hour"; git transport is not an API call ([GitHub REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). GitLab.com: "Authenticated API traffic for a user" 2,000/min, "Authenticated Git HTTPS traffic for a user" 10,000/min, "Git SSH operations for a user, project, and Git command" 600/min, single-project requests 400/min — so a per-run `default_branch` lookup over 1,000 repos *would* throttle, which is why layer 4 stays at discovery time; throttling is a `429` and for Projects/Groups/Users APIs carries no informational headers ([GitLab.com settings — rate limits](https://docs.gitlab.com/user/gitlab_com/)). Budget: discovery = O(repos/100) calls, pre-flight = 2, per-run sync = 0 ([wrapper-over-git.md sec. 6.4]).

### Non-interactive shell reality (source: `wrapper-over-git.md` sec. 4.6)

- A launchd or `ssh host 'zsh -c repo-sync'` shell is neither interactive nor login, so `/etc/zprofile`'s `path_helper` never runs and `/opt/homebrew/bin` is missing from `PATH`; `.zshrc` functions and aliases are absent; `zsh/parameter` and `zsh/zutil` are not auto-loaded ([zsh manual, Files](https://zsh.sourceforge.io/Doc/Release/Files.html)). Consequences: ship the wrapper as an executable file on `PATH` (`~/.local/bin/repo-sync`, `#!/bin/zsh -f`), set `path=(/opt/homebrew/bin /usr/local/bin $path)` at the top, `emulate -L zsh; setopt err_return pipe_fail no_unset no_monitor no_notify`, and `zmodload zsh/parameter zsh/zutil` explicitly ([wrapper-over-git.md sec. 4.6](https://zsh.sourceforge.io/Doc/Release/Files.html)).

### Trigger channels (source: `remote-and-agent-facing.md` sec. 1)

Six channels were compared; the recommendation combines two and defers a third.

- **Baseline unattended: `~/Library/LaunchAgents` plist with `StartCalendarInterval`, not `StartInterval`.** `StartInterval` firings are missed when "the system is asleep during the time of the next scheduled interval" and when "the job is running during an interval firing"; `StartCalendarInterval` instead "will start the job the next time the computer wakes up" and coalesces missed intervals into one event ([launchd.plist(5)](https://keith.github.io/xcode-man-pages/launchd.plist.5.html)). A LaunchAgent runs "on behalf of the logged in user" so the login Keychain and `SSH_AUTH_SOCK` are available; a LaunchDaemon survives logout but has neither ([Apple, Creating Launch Daemons and Agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html), [launchd.info](https://www.launchd.info/)). Set `ProcessType=Background`, explicit `PATH` in `EnvironmentVariables`, `StandardOutPath`/`StandardErrorPath`; leave `KeepAlive` unset ([launchd.plist(5)](https://keith.github.io/xcode-man-pages/launchd.plist.5.html)). `WatchPaths` gives a zero-cost local trigger: `ssh host touch ~/.sync-now` fires the job ([launchd.info](https://www.launchd.info/)); `launchctl kickstart gui/$(id -u)/<label>` over SSH is a complete trigger with zero new services ([launchd.info](https://www.launchd.info/)).
- **Remote trigger: SSH forced command.** An `authorized_keys` line `restrict,from="10.0.0.0/8",command="/Users/me/bin/repo-refresh-dispatch" ssh-ed25519 ...` pins a dedicated key to one command — "The command supplied by the user (if any) is ignored" — while `SSH_ORIGINAL_COMMAND` still carries the caller's request so one key can dispatch a small allowlist (`refresh all`, `refresh repo-x`, `status`); `restrict` disables PTY, port/agent/X11 forwarding and future restrictions in one word ([sshd(8)](https://man.openbsd.org/sshd.8)). `sshd` is a system daemon so this works while logged out, subject to FileVault unlocking the home volume ([remote-and-agent-facing.md sec. 1.1]). The dispatcher must validate `SSH_ORIGINAL_COMMAND` against an allowlist and take the same lock as every other entry point.
- **cron is ruled out on macOS**: `/usr/sbin/cron` is subject to TCC and fails with `Operation not permitted` on `~/Documents` (where this workshop's repos live) until the cron *binary* is granted Full Disk Access ([OS X Daily](https://osxdaily.com/2020/04/27/fix-cron-permissions-macos-full-disk-access/), [Apple Developer Forums 745692](https://developer.apple.com/forums/thread/745692)); it also skips jobs during sleep ([launchd.plist(5)](https://keith.github.io/xcode-man-pages/launchd.plist.5.html)). systemd timers (`Persistent=true`, built-in overlap protection) are the Linux analogue only ([systemd.timer(5)](https://man7.org/linux/man-pages/man5/systemd.timer.5.html)).
- **Forge webhooks are deferred.** GitLab disables a webhook "after 4 consecutive failures" temporarily and "after 40 consecutive failures; webhooks do not auto-re-enable" permanently, so a laptop that sleeps gets its hook killed within weeks; GitLab's own guidance is "Respond quickly with a `200`... Use a queue" ([GitLab Docs, Webhooks](https://docs.gitlab.com/user/project/integrations/webhooks/)); GitHub requires a 2XX "within 10 seconds" ([GitHub webhook best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)). Use them only via an always-on relay that records "changed" and calls the SSH trigger. Branch filter regex `^(main|master|release.*)$` keeps feature pushes out ([GitLab Docs, Webhooks](https://docs.gitlab.com/user/project/integrations/webhooks/)).
- **Claude Code scheduling must not perform the refresh.** `/loop` is session-bound; `/schedule` routines run on Anthropic cloud against cloud clones with a one-hour minimum and cannot touch `~/Documents` ([Anthropic, Introducing routines](https://claude.com/blog/introducing-routines-in-claude-code), [makerkit routines guide](https://makerkit.dev/blog/tutorials/claude-code-routines-guide), [wmedia.es](https://wmedia.es/en/tips/claude-code-schedule-vs-loop-vs-cron)); an LLM in the loop of a `git fetch` is the failure mode ("a hallucinated `git reset --hard`") this design exists to prevent ([remote-and-agent-facing.md sec. 1.6]).
- **MCP tool surface, phase 3**: a tiny stdio MCP server with `refresh_status` (read-only, `outputSchema` = the status contract, safe to auto-allow) and `refresh_repos {repos?, wait?}` (non-destructive; `isError: true` with per-repo detail when a repo failed — a tool-execution error, not a protocol error); validate `repos` against the allowlist and reuse the run lock as the rate limiter ([MCP Specification 2025-06-18, Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)). Keep it separate from codebase-memory-mcp so the memory server never holds network credentials; agents compose `refresh_repos → refresh_status → detect_changes → index_repository` ([remote-and-agent-facing.md sec. 1.7]).

### Mirror layout for agents (source: `remote-and-agent-facing.md` sec. 2)

- The `git-clone(1)` primitives decide what is safe: `--mirror` "sets up a refspec configuration such that all these refs are overwritten by a `git remote update`" — that is `+refs/*:refs/*`, which accepts a force-pushed `main`, so a mirror promising FF-only must use a refspec **without `+`** for protected branches or compare old/new with `merge-base --is-ancestor` and record `diverged: true` ([git-clone(1)](https://git-scm.com/docs/git-clone), [git-fetch(1)](https://git-scm.com/docs/git-fetch)). `--shared`/alternates are "a possibly dangerous operation": objects unreferenced in the *source* get pruned and "the cloned repository will become corrupt", so only the direction *human clone borrows from mirror* is safe, and even that is not worth the coupling for one developer unless repos are multi-GB ([git-clone(1)](https://git-scm.com/docs/git-clone)).
- Four layouts: A plain second clone (`B × (O + W)` disk); **B bare mirror + detached worktrees per branch** (`O + B × W`, one fetch); B+C alternates; **B+D snapshot worktrees behind a symlink flip** (`O + B × S × W`, full `W` written per changed branch). Recommendation for the stated setup is **B + D**: the bare mirror is the only thing that fetches so credentials live in one place, detached worktrees cannot be moved by a stray `git pull`, and the flip makes "never half-updated" true regardless of who is reading ([remote-and-agent-facing.md sec. 2.6](https://git-scm.com/docs/git-worktree)). A bare repo can own linked worktrees ("zero or more linked worktrees"), `--lock --reason` tags them, and `git worktree repair` is needed if the mirror root ever moves — treat the mirror root as a fixed path ([git-worktree(1)](https://git-scm.com/docs/git-worktree)).
- Path subtlety for codebase-memory-mcp: if it records the symlink path it follows every flip (desired for `detect_changes`); if it `realpath`s it holds a snapshot due for deletion — hence the contract publishes both paths and a deletion grace period ([remote-and-agent-facing.md sec. 2.5]).
- Reference implementation is kubernetes/git-sync: "git checkouts are not 'atomic' operations"; it "fetches data without checking it out, creates a new worktree, then updates the symlink", worktrees are "named by the git hash of its revision" so `readlink` alone yields the current commit; `--exechook-command`/`--webhook-url` fire after sync and are "not guaranteed exactly-once", so consumers key idempotency on the hash; `--stale-worktree-timeout` defaults to 0 (immediate removal), which is too aggressive for multi-agent readers ([kubernetes/git-sync README](https://github.com/kubernetes/git-sync/blob/master/README.md)).
- `FETCH_HEAD` mtime tells you when refs were last listed but not whether the FF check passed or the worktree flip completed; bare repos have `core.logAllRefUpdates` **off by default** ("defaults to true in repositories with working directories and false in bare repositories"), so enable it at mirror creation to get the per-branch audit trail ([Documentation/config/core.adoc](https://github.com/git/git/blob/master/Documentation/config/core.adoc)). A pruned `release*` branch should appear as `state: "removed"` for one cycle before its worktree is deleted ([remote-and-agent-facing.md sec. 3.2]).

### Freshness contract for agents (source: `remote-and-agent-facing.md` sec. 3)

- **One JSON document, one writer, rename-replaced.** `~/mirrors/.status/refresh.json` written as `.tmp` + `fsync` + `rename` by the refresh script only, while holding the lock; the MCP `refresh_status` tool returns it verbatim ([remote-and-agent-facing.md sec. 3.5]). The document is rewritten once at the end of a run, so readers finding `run.state = running` use the previous `repos` data and re-check after `expected_duration_seconds`; a `running` state with a dead `pid` older than `2 × expected_duration_seconds` is treated as abandoned ([remote-and-agent-facing.md sec. 3.5]).
- **Fields that matter**: `run {run_id, state idle|running|failed, trigger launchd|ssh|mcp|manual, started_at, finished_at, pid, expected_duration_seconds}`, `last_success_at` (moves only when *every* repo reached `ok`/`unchanged`), `retain_previous_for_seconds`, and per repo `{remote, mirror, fetched_at, state ok|unchanged|diverged|auth_failed|network_failed|removed, consecutive_failures, error, branches{<b>: {project, path, snapshot_path, commit, previous_commit, committed_at, changed, fast_forward, notes.persistence_unsafe}}}` ([remote-and-agent-facing.md sec. 3.5]). `git fetch --porcelain` output (`<flag> <old-oid> <new-oid> <local-ref>`) supplies `previous_commit`/`commit` for free ([git-fetch(1)](https://git-scm.com/docs/git-fetch)).
- **Why the consumers force three fields.** From the live codebase-memory-mcp tool schemas: `index_repository` derives the project name from `repo_path` unless `name` is passed — so a symlink whose basename is `main` for every repo would collide all repos into one project, and a `main@<sha>` snapshot path would create a project per commit; hence the explicit `project` field (`orders-service@main`) passed as `name` and as `project` to `detect_changes`/`index_status`. `detect_changes` takes `since` as a git ref and diffs `<since>...HEAD`; the SHA the agent last indexed always resolves in the shared object store, so agents remember `last_indexed_commit` and fall back to `previous_commit`. `persistence: true` writes `.codebase-memory/graph.db.zst` *inside* the snapshot, which is deleted on rotation — flagged `notes.persistence_unsafe` ([remote-and-agent-facing.md sec. 3.4]).
- **Agent decision rule**: running and not abandoned → wait, re-read; per project: `auth_failed|network_failed|diverged` → use existing index, surface error; never indexed → `index_repository(path, name=project)`; `changed` → `detect_changes(project, since=last_indexed_commit)` then `index_repository(mode=fast|moderate)` if large; else nothing; record `last_indexed_commit = commit`. `cross-repo-intelligence` only when `last_success_at` is newer than every target's last index ([remote-and-agent-facing.md sec. 3.5]).
- **Lock scope**: held across *fetch → verify FF → create snapshot worktree → flip symlink → write status → prune*, not just the fetch, because `git clone --local` "can race with concurrent modification to the source repository" and `worktree add` reads the object store ([git-clone(1)](https://git-scm.com/docs/git-clone)). Readers never take the lock. A second trigger while running prints the current status and exits 0 rather than queuing ([remote-and-agent-facing.md sec. 3.3]).

### Unattended credentials (source: `remote-and-agent-facing.md` sec. 4)

- **GitLab primary over SSH: a passphrase-less ed25519 deploy key**, read-only by default ("A read-only deploy key can only read from the repository"), enabled per project or as a public deploy key across projects, needs Maintainer/Owner to add, Free tier ([GitLab Docs, Deploy keys](https://docs.gitlab.com/user/project/deploy_keys/)). Wire it with `core.sshCommand` per mirror = `ssh -i ~/.ssh/mirror_deploy_ed25519 -o IdentitiesOnly=yes -o IdentityAgent=none -o BatchMode=yes` — `IdentitiesOnly` stops ssh offering the human's keys first (GitLab counts failed offers), `IdentityAgent=none` makes the run identical with and without a login session, `BatchMode` fails instead of hanging on a prompt that would hold the lock ([git(1) GIT_SSH_COMMAND](https://git-scm.com/docs/git#Documentation/git.txt-codeGITSSHCOMMANDcode)). Forwarding the human's `ssh-agent` is rejected: absent for LaunchDaemons and post-reboot SSH, carries push rights the job never needs, and `restrict` disables agent forwarding anyway ([sshd(8)](https://man.openbsd.org/sshd.8)).
- **HTTPS fallback**: GitLab deploy token (`read_repository` only, "Deploy tokens can't be used with the GitLab public API", no forced expiry, Free tier, HTTPS only) ([GitLab Docs, Deploy tokens](https://docs.gitlab.com/user/project/deploy_tokens/)); or project/group access token with `read_repository` — 365-day default expiry cap, so the job **will** stop once a year and rotation makes "the original token ... inactive immediately", hence write-new-secret-first-then-rotate and a T-14-day warning in the status document ([GitLab Docs, Project access tokens](https://docs.gitlab.com/user/project/settings/project_access_tokens/), [Personal access tokens](https://docs.gitlab.com/user/profile/personal_access_tokens/)). GitHub secondary: fine-grained PAT, selected repos, `Contents: read` ([GitHub Docs, Managing PATs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)). Supply via a `!` credential helper that answers only `get` from a `chmod 600` file, after `git config credential.helper ""` in the mirror's own config to evict the global `osxkeychain` ([gitcredentials(7)](https://git-scm.com/docs/gitcredentials)). With per-project deploy tokens set `credential.useHttpPath = true`, since git by default "does not consider the 'path' component" ([gitcredentials(7)](https://git-scm.com/docs/gitcredentials)).
- **The login keychain is a trap under launchd/SSH-at-night**: a different binary asking for an item triggers a GUI allow dialog that cannot show, and `set-keychain-settings -l`/`-u` lock it on sleep or timeout ([security(1)](https://keith.github.io/xcode-man-pages/security.1.html), [Apple Support, login keychain](https://support.apple.com/guide/keychain-access/if-your-mac-keeps-asking-for-the-login-keychain-password-kyca1242/mac)). Recommendation: secret in a `chmod 600` file on the FileVault volume; keychain reserved for the human ([remote-and-agent-facing.md sec. 4.7]).
- **CLIs are not on the unattended path.** If used for health checks: `GH_TOKEN` "takes precedence over previously stored credentials", `GH_PROMPT_DISABLED`, `GH_NO_UPDATE_NOTIFIER`, `GH_HOST` ([gh help environment](https://cli.github.com/manual/gh_help_environment)); `GITLAB_TOKEN` "Set this variable to avoid prompts", `GLAB_NO_PROMPT`, `GLAB_CHECK_UPDATE`, `GITLAB_HOST` ([GitLab CLI docs](https://docs.gitlab.com/cli/)). `glab repo list` needs `read_api`, which bends the `read_repository`-only rule — so discovery stays out of the unattended job ([remote-and-agent-facing.md sec. 4.5]).

### Prior art worth copying (source: `remote-and-agent-facing.md` sec. 5)

- **Sourcegraph repo-updater**: per-repo adaptive backoff — "if a repository's last commit was 8 hours ago, then the next sync will be scheduled 4 hours from now", bounded "never ... more frequently than 45 seconds, and no less frequently than every 8 hours"; discovery (`repoListUpdateInterval`) is a separate loop from content fetch ([Sourcegraph, Repository update frequency](https://docs.sourcegraph.com/admin/repo/update_frequency), [Site configuration](https://docs.sourcegraph.com/admin/config/site_config)). Copy: skip quiet repos on most ticks with a daily ceiling; SSH/MCP triggers bypass the backoff.
- **Google repo manifest**: `<remote fetch>`, `<default revision sync-j sync-c>`, `<project name path revision groups clone-depth>` ([git-repo manifest-format.md](https://gerrit.googlesource.com/git-repo/+/HEAD/docs/manifest-format.md)). Copy: a human-edited manifest with those fields keyed by the same names the status document uses.
- **Backstage catalog**: jitter ("choose random numbers in that range to spread out the load") and a visible orphan state over silent deletion ([Backstage, Software Catalog configuration](https://backstage.io/docs/features/software-catalog/configuration/)).
- **GitLab pull mirroring** validates the defaults: "Automatically, 30 minutes after a previous pull", manual updates floor at 5 minutes, "GitLab halts updates when branches diverge to prevent data loss", "Only mirror protected branches", "After 14 failures, a mirror is marked as a hard failure" ([GitLab Docs, Pull from a remote repository](https://docs.gitlab.com/user/project/repository/mirror/pull/)). GitHub's own mirror recipe warns "all local references will be overwritten each time you fetch" and that bare mirrors hold no LFS objects — snapshots of LFS repos need `git lfs fetch`/`checkout` ([GitHub Docs, Duplicating a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/duplicating-a-repository)).

## Contradictions and tensions

The three files agree on the invariants (fetch is the only network step; every local ref move is FF-or-nothing; dirty trees are skipped; readers get a `rename(2)` flip; forge CLIs stay out of the hot loop). They disagree on mechanism in the places below, each with the resolution this synthesis adopts.

1. **Where the reader tree lives: linked worktree of the human's clone (`wrapper-over-git.md` policy C) vs separate bare mirror (`remote-and-agent-facing.md` layout B+D).** Policy C shares the human clone's object store — one fetch, one credential, minimal disk — and relies on the human's clone as the object source ([git-worktree(1)](https://git-scm.com/docs/git-worktree)). Layout B+D pays a second object store and a second fetch for total isolation: the human's `.git` is never opened by the unattended job, and a corrupted or relocated human clone cannot break the agents' view ([git-clone(1)](https://git-scm.com/docs/git-clone)). Both agree on detached worktrees and on a `rename(2)`-based symlink flip; they disagree only on which repository owns the worktrees. **Resolution: linked worktrees of the human's clone (C+D) first.** The research question asks for the human's major branches to be kept current, so the human clone is fetched anyway; a bare mirror would double every fetch and add a second inventory. The isolation argument for B+D is answered by injecting the deploy key via `GIT_SSH_COMMAND` only in the wrapper process — so the wrapper never depends on the login session and never edits the human's git config — and by `-c core.hooksPath=/dev/null` on every wrapper call. **Migrate to a bare mirror if** the human clones are routinely deleted or moved (linked worktrees then need `git worktree repair` — [git-worktree(1)](https://git-scm.com/docs/git-worktree)), or if the agents must survive a human `git gc`/`repack` on a clone with unusual settings. The status document is designed so readers cannot tell which layout is behind it ([remote-and-agent-facing.md sec. 2.6]).

2. **Force-pushed protected branch: follow the forge or halt?** `wrapper-over-git.md` says a detached reader worktree "always tracks `origin/<branch>` exactly, including after a force-push on the forge", and calls that desirable for a knowledge base ([wrapper-over-git.md sec. 3.5](https://git-scm.com/docs/git-worktree)); `remote-and-agent-facing.md` says "The mirror is **not** updated, the old snapshot stays current" and records `state: diverged`, matching GitLab's own "halts updates when branches diverge" default ([remote-and-agent-facing.md sec. 3.5], [GitLab Docs, Pull mirroring](https://docs.gitlab.com/user/project/repository/mirror/pull/)). **Resolution:** the human's *local* branch is never force-moved (git's refusal handles it — [git-fetch(1)](https://git-scm.com/docs/git-fetch)); the reader snapshot follows the forge but stamps `fast_forward: false` and bumps `consecutive_failures`-style visibility so agents do a full re-index instead of `detect_changes`; `--halt-on-diverge` makes the snapshot behave like GitLab. Default is follow-and-flag because a KB that silently lags the forge for days is the worse outcome for read-only consumers.

3. **Two fixed slots vs per-SHA snapshots.** `wrapper-over-git.md` recommends `slot-a`/`slot-b` and notes a reader job stays consistent only "until the flip *after* the next one" ([wrapper-over-git.md sec. 5.4.2]); `remote-and-agent-facing.md` and git-sync name each snapshot by hash with a retention timeout ([kubernetes/git-sync README](https://github.com/kubernetes/git-sync/blob/master/README.md)). **Resolution:** per-SHA snapshots with `retain_previous_for_seconds` (default 1800); two slots are the degenerate S=2 case and break long `index_repository` runs. Cost is a full working-tree write per changed branch, negligible for service repos, and the reason to measure `du -sh` on the user's largest checkout first ([remote-and-agent-facing.md sec. 2.7]).

4. **Second trigger while running: exit 3 or exit 0?** `wrapper-over-git.md` reserves exit `3` for "lock held" so a remote trigger can retry ([wrapper-over-git.md sec. 4.4]); `remote-and-agent-facing.md` says "exit 0 with the current status document on stdout" ([remote-and-agent-facing.md sec. 3.3]). **Resolution:** exit 3 *and* print `refresh.json`; the SSH dispatcher and the MCP tool translate 3 into `state: "running"` without `isError`, so scripts get a distinct code and agents get a non-error.

5. **Stash vs skip for dirty trees.** All three files land on skip; only `wrapper-over-git.md` costs out stash and disqualifies it for unattended use ([git-stash(1)](https://git-scm.com/docs/git-stash)); gitup's README independently skips dirty trees ([gitup README](https://github.com/earwig/git-repo-updater)). No contradiction, but note the residual gap: a permanently dirty clone never refreshes its *checked-out* branch, which is invisible to agents (they read snapshots) but should show as "skipped for N consecutive runs" for the human ([wrapper-over-git.md sec. 3.3]).

6. **Parallelism: unbounded vs 4.** gita fans out every repo at once with no semaphore ([gita/utils.py](https://github.com/nosarthur/gita/blob/master/gita/utils.py)); the wrapper file starts at 4 ([wrapper-over-git.md sec. 4.3.5]); GitLab.com caps "Git SSH operations for a user, project, and Git command" at 600/min ([GitLab.com rate limits](https://docs.gitlab.com/user/gitlab_com/)). **Resolution:** `-P 4`, raise to 8 only after measuring; never loop-retry inside a job.

7. **Credentials from launchd: keychain/`SSH_AUTH_SOCK` vs deploy key.** `existing-cli-tools.md` proposes pointing `SSH_AUTH_SOCK` at the user's agent or relying on `osxkeychain` from a LaunchAgent ([existing-cli-tools.md sec. 4.1]); `remote-and-agent-facing.md` shows both fail for a LaunchDaemon, a night-time SSH trigger, or a locked keychain, and that the human's key carries push rights the job never needs ([security(1)](https://keith.github.io/xcode-man-pages/security.1.html), [GitLab Docs, Deploy keys](https://docs.gitlab.com/user/project/deploy_keys/)). **Resolution:** deploy key via `GIT_SSH_COMMAND` in the wrapper process only.

8. **`StartInterval` vs `StartCalendarInterval`.** `existing-cli-tools.md` lists both as options ([launchd.info](https://www.launchd.info/)); `remote-and-agent-facing.md` shows `StartInterval` "will be missed" during sleep and while the job runs ([launchd.plist(5)](https://keith.github.io/xcode-man-pages/launchd.plist.5.html)). **Resolution:** `StartCalendarInterval` array `[{Minute:0},{Minute:30}]`.

9. **gitup first vs hand-roll.** `existing-cli-tools.md` says "try gitup first" ([existing-cli-tools.md sec. 5.3]); this synthesis does not, because the other two files show the requirement is dominated by publish and contract, which no tool provides, and because every tool's exit-code behaviour is unverified. gitup remains a fine *interactive* convenience for the human's own clones; it is simply not the engine.

10. **`--mirror` semantics.** `remote-and-agent-facing.md` warns a `--mirror` clone's `+refs/*:refs/*` accepts force-pushes ([git-clone(1)](https://git-scm.com/docs/git-clone)); `wrapper-over-git.md` says the `+` on `refs/remotes/*` is correct and only dangerous on `refs/heads/*` ([git-fetch(1) refspec](https://git-scm.com/docs/git-fetch#_refspec_)). Both are right for their layout; in the C+D layout the default clone refspec is kept, and FF-only is enforced where it matters, at `fetch b:b` / `merge --ff-only`.

11. **codebase-memory-mcp `persistence`** writes into the snapshot directory that rotation deletes ([remote-and-agent-facing.md sec. 3.4]). Not a contradiction between files, but a live conflict between the memory server's feature and the publish strategy; the contract flags it rather than solving it.

## Next step: implementation spec

### Name and shape

- `~/.local/bin/repo-sync` — one executable file, `#!/bin/zsh -f`, `emulate -L zsh; setopt err_return pipe_fail no_unset no_monitor no_notify; zmodload zsh/system zsh/parameter zsh/zutil; autoload -Uz zargs; path=(/opt/homebrew/bin /usr/local/bin $path)` at the top ([wrapper-over-git.md sec. 4.6](https://zsh.sourceforge.io/Doc/Release/Files.html)). A file on `PATH`, not a `.zshrc` function, so launchd, `ssh host zsh -c`, and `zargs` children all find it.
- `~/.local/bin/repo-sync-dispatch` — the SSH forced-command target; allowlists `SSH_ORIGINAL_COMMAND` ∈ {`sync`, `sync <name>`, `status`} and execs `repo-sync` accordingly ([sshd(8)](https://man.openbsd.org/sshd.8)).
- Subcommands: `repo-sync [sync] [flags]` (default), `repo-sync status [--json]`, `repo-sync init` (first-touch config, reader dirs, `git maintenance register`), `repo-sync discover` (gh/glab enumeration → `discovered.tsv`, report-only).

### Config: `~/.config/repo-sync/manifest.tsv`

Tab-separated, `#` comments, blank lines ignored, `~` expanded, validated with `git rev-parse --show-toplevel` and `sort -u` before the parallel phase ([wrapper-over-git.md sec. 4.1]). Fields borrowed from Google repo's manifest ([git-repo manifest-format.md](https://gerrit.googlesource.com/git-repo/+/HEAD/docs/manifest-format.md)):

```
# path	name	branches	groups
~/Documents/src/orders-service	orders-service	main,release*	payments,backend
~/Documents/src/legacy-api	legacy-api	master	backend
```

`branches` defaults to `main,master,release*` (whichever exist); `name` defaults to the basename and is the key used in `refresh.json` and in `project = <name>@<branch>`. Environment overrides: `REPO_SYNC_MANIFEST`, `REPO_SYNC_STATE` (default `${XDG_STATE_HOME:-~/.local/state}/repo-sync`), `REPO_SYNC_READERS` (default `${XDG_DATA_HOME:-~/.local/share}/repo-sync/readers`), `REPO_SYNC_JOBS` (default 4), `REPO_SYNC_DEPLOY_KEY` (default `~/.ssh/repo_sync_ed25519`), `REPO_SYNC_RETAIN` (default 1800 s).

### Flags

| Flag | Effect |
|---|---|
| `--repo NAME` (repeatable), `--group G` | subset of the manifest; default all |
| `--dry-run` | `git fetch --dry-run`; nothing written under `refs/` or the readers; results tagged `DRYRUN` ([git-fetch(1)](https://git-scm.com/docs/git-fetch)) |
| `--fetch-only` | real fetch, prints the FF delta via `%(upstream:trackshort)`, no branch moves, no publish ([git-for-each-ref(1)](https://git-scm.com/docs/git-for-each-ref)) |
| `--strict` | `SKIPPED`/`DIVERGED` count toward exit 1 |
| `--allow-untracked` | `?` entries do not make a tree dirty |
| `--stash` | policy B for the checked-out branch; off by default, documented as unsafe unattended ([git-stash(1)](https://git-scm.com/docs/git-stash)) |
| `--no-readers` | skip the publish step |
| `--no-backoff` | ignore the per-repo quiet-repo backoff (set by the SSH/MCP dispatchers) |
| `--halt-on-diverge` | keep the old reader snapshot when `origin/<b>` is not a descendant of the previous snapshot |
| `--jobs N`, `--trigger launchd|ssh|mcp|manual`, `--json` | concurrency; recorded in `run.trigger`; print `refresh.json` on stdout at exit |

### Exit codes

`0` all repos `OK`/`UPTODATE` (or `SKIPPED`/`DIVERGED` without `--strict`); `1` any `FAILED` (or skips under `--strict`); `2` usage, manifest, or pre-flight error — nothing touched; `3` run lock held — `refresh.json` printed, callers treat as "running"; `124` reserved for an outer `timeout` ([wrapper-over-git.md sec. 4.4]). `zargs` returns 123 internally when any child failed; the parent recomputes the code from the `.result` files, never from `zargs` alone ([zargs](https://github.com/zsh-users/zsh/blob/master/Functions/Misc/zargs)).

### Lock strategy

- Global: `: >> $STATE/run.lock; zsystem flock -t 0 -f lockfd $STATE/run.lock || exit 3` — kernel lock, self-releasing on any exit; the parent stays alive until `wait` returns so children inherit, never outlive, the lock ([zsh/system](https://github.com/zsh-users/zsh/blob/master/Doc/Zsh/mod_system.yo)).
- Per repo: `zsystem flock -t 5` on `$(git -C $repo rev-parse --git-common-dir)/repo-sync.lock`, held across fetch → classify → branch moves → snapshot → flip → result write ([wrapper-over-git.md sec. 5.2], [remote-and-agent-facing.md sec. 3.3]).
- Git's own locks: `--no-optional-locks` on every `status`; "cannot lock ref" / `index.lock` → `FAILED reason=lock`, no in-job retry, never delete `index.lock` ([Documentation/config/core.adoc](https://github.com/git/git/blob/master/Documentation/config/core.adoc)).
- Readers never lock; a run in progress is signalled by `run.state` and the lock file's presence only.

### Per-repo refresh (the human's clone)

```
env: GIT_TERMINAL_PROMPT=0 GIT_SSH_COMMAND="ssh -i $KEY -o IdentitiesOnly=yes -o IdentityAgent=none -o BatchMode=yes -o ConnectTimeout=10"
git -c core.hooksPath=/dev/null -c fetch.prune=true -c merge.ff=only -c pull.rebase=false -C $repo \
    fetch --prune --atomic --porcelain --no-write-fetch-head origin            # + 'refs/heads/release*:refs/remotes/origin/release*' when release* requested
git -C $repo remote set-head origin -a                                          # default branch, after fetch
classify: --no-optional-locks status --porcelain=v2 -z --untracked-files=normal --show-stash ; marker files under rev-parse --absolute-git-dir
for b in resolved branches:
  b checked out anywhere (%(worktreepath))  → tree clean ? merge --ff-only refs/remotes/origin/$b : SKIPPED dirty|REBASE|MERGING…
  else                                       → git fetch origin $b:$b            # FF-only and checked-out refusal built in; rejection → DIVERGED
```

Sources: [git-fetch(1)](https://git-scm.com/docs/git-fetch), [git-merge(1)](https://git-scm.com/docs/git-merge), [git-remote(1)](https://git-scm.com/docs/git-remote#Documentation/git-remote.txt-emset-headem), [git-status(1)](https://git-scm.com/docs/git-status), [git-prompt.sh](https://github.com/git/git/blob/master/contrib/completion/git-prompt.sh), [git(1) GIT_SSH_COMMAND](https://git-scm.com/docs/git#Documentation/git.txt-codeGITSSHCOMMANDcode).

### Publish strategy (readers)

```
$READERS/<name>/
  .snapshots/<b-slug>@<sha>/      detached, locked worktree of the human's clone: git -C $repo worktree add --detach --lock --reason "repo-sync reader" <dir> refs/remotes/origin/<b>
  <b-slug>  -> .snapshots/<b-slug>@<sha>   relative symlink; <b-slug> = branch with '/' → '__'
  <b-slug>/.repo-sync.json        {commit, previous_commit, fast_forward, published_at} written before the flip
```

Flip: `ln -sfn .snapshots/<b-slug>@<sha> $READERS/<name>/<b-slug>.tmp && mv -h $READERS/<name>/<b-slug>.tmp $READERS/<name>/<b-slug>` — one `rename(2)`; readers and snapshots on the same APFS volume ([rename(2)](https://keith.github.io/xcode-man-pages/rename.2.html), [mv(1) macOS](https://keith.github.io/xcode-man-pages/mv.1.html)). Prune: after the run, `git worktree remove` (refuses unclean trees — free guard) then `git worktree prune` for snapshots not targeted by a symlink and older than `REPO_SYNC_RETAIN` ([git-worktree(1)](https://git-scm.com/docs/git-worktree)). If `origin/<b>` is not a descendant of the previous snapshot's SHA (`merge-base --is-ancestor`), publish anyway with `fast_forward: false` unless `--halt-on-diverge` ([git-merge-base(1)](https://git-scm.com/docs/git-merge-base#Documentation/git-merge-base.txt---is-ancestor)). LFS repos: `git -C <dir> lfs checkout` after `worktree add` ([GitHub Docs, Duplicating a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/duplicating-a-repository)).

### Freshness stamp

- `$STATE/refresh.json`, `schema_version: 1`, written once per run as `.tmp` → `fsync` → `rename` while the lock is held; fields exactly as in the contract above with `mirror` replaced by `repo` (absolute path of the human's clone) and `readers_root` added at top level ([remote-and-agent-facing.md sec. 3.5]). Timestamps RFC 3339 UTC (`date -u +%Y-%m-%dT%H:%M:%SZ`); `run_id = <timestamp>-<4 hex>`; SHAs full 40-hex.
- `$STATE/runs/<run_id>/{<slug>.log, <slug>.result, summary.tsv}` and `$STATE/latest` symlink flipped after `summary.tsv` exists; `.result` columns `status repo branch before_sha after_sha reason seconds`, status ∈ {`OK`,`UPTODATE`,`SKIPPED`,`DIVERGED`,`FAILED`} ([wrapper-over-git.md sec. 4.4]).
- Backoff: skip a repo on a launchd tick when its newest `committed_at` is older than 24 h *and* it was fetched within the last 6 h; always fetch at least daily; `--no-backoff` bypasses ([Sourcegraph, Repository update frequency](https://docs.sourcegraph.com/admin/repo/update_frequency)).

### Minimal remote-trigger channel to build first

1. `repo-sync` itself, run by hand, until fault injection passes.
2. `~/Library/LaunchAgents/local.repo-sync.plist`: `ProgramArguments [/bin/zsh, -f, -c, "$HOME/.local/bin/repo-sync --trigger launchd"]`, `StartCalendarInterval [{Minute:0},{Minute:30}]`, `ProcessType Background`, `EnvironmentVariables {PATH, GIT_TERMINAL_PROMPT=0, GH_PROMPT_DISABLED=1, GLAB_NO_PROMPT=1}`, `StandardOutPath`/`StandardErrorPath` under `~/Library/Logs/repo-sync/`; load with `launchctl bootstrap gui/$(id -u)`, fire on demand with `launchctl kickstart gui/$(id -u)/local.repo-sync` ([launchd.plist(5)](https://keith.github.io/xcode-man-pages/launchd.plist.5.html), [launchd.info](https://www.launchd.info/)).
3. Remote: generate `~/.ssh/repo_sync_trigger_ed25519` on the *other* machine; on the Mac add `restrict,from="<vpn cidr>",command="/Users/<me>/.local/bin/repo-sync-dispatch" ssh-ed25519 AAAA... trigger@laptop` to `authorized_keys`; enable Remote Login. The caller runs `ssh mac sync` or `ssh mac status`; the dispatcher execs `repo-sync --trigger ssh --no-backoff --json` and maps exit 3 to a "running" message ([sshd(8)](https://man.openbsd.org/sshd.8)).
4. Only after 1–3 are stable: the two-tool stdio MCP server (`refresh_status`, `refresh_repos`) that shells out to `repo-sync --json` and returns the file as `structuredContent` ([MCP 2025-06-18 Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)).

### Definition of done for the first cut

Fault-injection matrix passes (dead remote → `FAILED`, exit 1; dirty tree → `SKIPPED`, refs and reader still refreshed; mid-rebase → `SKIPPED reason=REBASE`; local commits on `main` → `DIVERGED`; second concurrent run → exit 3 with JSON on stdout); `zsh -f -c` self-test finds `git` and the deploy key ([wrapper-over-git.md sec. 4.6]); `index_repository(repo_path=<reader path>, name=<name>@main)` then `detect_changes(project, since=<previous_commit>)` succeed against a published snapshot.
