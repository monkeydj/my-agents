## 1. Executive Summary (3-5 bullets)

- **All three patterns solve the same core problem the same basic way**: split AI-coding work into small, persisted, human-reviewed artifacts instead of one long chat, and reset context between stages so the agent stays focused (per rpi-framework.md Section 1, wayfinder-prototype.md Sections 2-4, qrspi.md Section 5). The consequence: none of the three is a genuinely novel idea — they are three implementations of "frequent intentional compaction," HumanLayer's own name for the underlying technique (rpi-framework.md, Section 1).
- **QRSPI and HumanLayer's "CRISPY" are very likely the same proposal, not two frameworks** — both trace to one Dex Horthy talk in March 2026, per a secondary source that states QRSPI "is also referred to as CRISPY" and cites a talk literally titled "CRISPY / QRSPI Framework Talk" (qrspi.md, Section 1). Confidence on the identity claim is medium-high; confidence on the exact phase list is low, because the two research passes' secondary sources give non-matching phase names for what they claim is the same talk (see Section 2 note below). Treat this as one option under two names, with the details unconfirmed.
- **RPI is the simplest and best-documented of the three, but its own creator has already moved past it.** HumanLayer replaced RPI internally because teams stopped reading generated code and plans grew too complex to review at scale (rpi-framework.md, Section 1) — a warning sign for anyone adopting RPI as a permanent, not transitional, practice.
- **Wayfinder+Prototype is the most production-grade tooling of the three** (official Claude Code marketplace plugin, explicit HITL/AFK typing per ticket, generic non-Claude-Code installer) but carries the heaviest setup cost: an issue tracker must be configured before it works at all (wayfinder-prototype.md, Section 5).
- **This repo already implements most of RPI/QRSPI's core discipline natively**, via `me-draft` → `me-craft` (plan then build, human-gated handoff) and `pickup` (persist-to-file, reset-context, reload). The two concrete, low-cost gaps worth closing are a separable, ticket-hidden Research artifact and a soft ~200-line plan-doc size cap — see Section 7.

## 2. Side-by-Side Comparison

**On QRSPI/CRISPY, stated plainly before the table**: qrspi.md found that "QRSPI" and rpi-framework.md's "CRISPY" are very likely the same Dex Horthy proposal (one March 2026 talk, "CRISPY / QRSPI Framework Talk"), described under two different names by two different secondary sources (qrspi.md Section 1, citing alexlavaee.me's "From RPI to QRSPI"). But the two files' secondary sources disagree on the actual phase list: rpi-framework.md's source (ZenML LLMOps Database) expands CRISPY as "Context-Research-Iterate-Structure-Plan-sYnthesize" (7 stages); qrspi.md's closest-to-primary source (a blog account of Horthy's own talk) gives 8 phases — Questions→Research→Design Discussion→Structure Outline→Plan→Work Tree→Implement→Pull Request — with no shared phase names against the CRISPY acronym. Neither research pass found a HumanLayer-published primary document using either name. **Confidence: medium-high that QRSPI and CRISPY are the same underlying proposal; low on the exact phase count/names.** The table below lists QRSPI/CRISPY as one row, not two, and flags this uncertainty inline rather than presenting either phase list as settled.

## 3. Where They Overlap

- **Persisted artifacts over live conversation.** All three write structured markdown (or tracker issues) to disk instead of keeping planning inside one long chat — RPI's `thoughts/*.md` files, Wayfinder's Map/Ticket issues, QRSPI's numbered phase files (rpi-framework.md §2-3; wayfinder-prototype.md §2; qrspi.md §3). Consequence: any of the three lets a human review intent before code exists, catching a wrong assumption while it's still cheap to fix.
- **Context reset between planning stages.** RPI names this explicitly ("fresh session per phase"); Wayfinder enforces it implicitly via one-ticket-per-session; QRSPI names it explicitly and adds the ticket-hiding trick (rpi-framework.md §1, §5; wayfinder-prototype.md §2; qrspi.md §2-3). Consequence: none of the three trusts a single long-lived context window to stay reliable across a whole multi-step task — this is the one mechanic none of them treats as optional.
- **Mandatory human review gate before execution.** Every framework blocks moving from planning to code without a human checkpoint — RPI's FAR/FACTS scales, Wayfinder's HITL ticket types, QRSPI's post-Design/Structure/Validate gates (rpi-framework.md §2-3; wayfinder-prototype.md §2; qrspi.md §3). Consequence: in all three, skipping this gate is a documented anti-pattern, not just an omission.
- **Explicit ceremony triage.** Every framework tells the user when *not* to use it — RPI skips for single-file/obvious fixes, Wayfinder skips to `/grill-with-docs` when the path is clear, QRSPI's dfrysinger variant scales via four ceremony tiers (rpi-framework.md §6; wayfinder-prototype.md §5; qrspi.md §4). Consequence: none of the three is meant to run unconditionally on every task — all three assume a triage step exists somewhere, which is the same job this repo's `rules/decision-gates.md` already does generically (see Section 6).
- **Parallel subagent research.** RPI's `find_files`/`analyze_code`/`find_patterns`, Wayfinder's `research` skill run as a background subagent, and QRSPI's `codebase-locator`/`codebase-analyzer`/`codebase-pattern-finder` companion agents are functionally the same three-way split of "locate, read, find precedent" (rpi-framework.md §2; wayfinder-prototype.md §4; qrspi.md §4).
- **Shared root narrative.** RPI and QRSPI/CRISPY trace to the same source lineage (HumanLayer/Dex Horthy) by direct claim (rpi-framework.md §1; qrspi.md §1). Wayfinder does not claim RPI lineage — its overlap with the other two is philosophical convergence (Pocock's own framing: "you're managing the context of the agent you're working in," per wayfinder-prototype.md §5), not shared authorship.

## 4. Where They Diverge

- **Unit of work differs fundamentally.** RPI and QRSPI plan around **tasks** — a plan document is a sequence of build steps. Wayfinder plans around **decisions** — a ticket is a question to resolve, not a task to execute; the skill's own words: "Wayfinding is about finding that way, not charging at the destination" (wayfinder-prototype.md §2). This is a genuinely different mental model, not a naming difference — RPI/QRSPI implicitly assume the destination is already known and only the steps need planning; Wayfinder is built for when the destination itself is still unclear.
- **Storage medium.** RPI and QRSPI are file-native (markdown in a `thoughts/`-style directory tracked in git). Wayfinder is tracker-native (GitHub Issues/GitLab Issues/Jira, using the tracker's own blocking-dependency feature so the "frontier" of unblocked work is visible in the tracker UI itself, not just in a file) (rpi-framework.md §2-3; wayfinder-prototype.md §2). Consequence: Wayfinder requires infrastructure (a configured issue tracker) that RPI and QRSPI don't.
- **Ceremony weight varies widely.** RPI is fixed at 3 phases. QRSPI ranges 5-8 depending on variant. Wayfinder has no fixed phase count at all — it resolves however many tickets the fog requires, one per session, until nothing is left to decide (rpi-framework.md §2-4; qrspi.md §2; wayfinder-prototype.md §2). RPI is the lightest by construction; QRSPI's 8-phase variant is the heaviest of any single fixed structure found.
- **Prototype-as-executable-artifact has no equivalent in RPI or QRSPI.** Both RPI and QRSPI treat "design" as a markdown document (a Design/Structure phase). Wayfinder's `prototype` skill produces runnable code — a shareable HTML file or a multi-variant UI route — specifically because some questions ("does this state model feel right," "what should this look like") resist being settled by prose alone (wayfinder-prototype.md §3). Consequence: RPI/QRSPI users answering a UI/logic design question have no named mechanic for this inside their own framework; Wayfinder does.
- **Anti-bias mechanics differ.** QRSPI's "hide the ticket during Research" is a specific, repeated, mechanical safeguard against the agent's research being shaped by the solution it expects to propose (qrspi.md §2-3, corroborated across all 4 variants checked). Neither RPI's nor Wayfinder's sources describe an equivalent safeguard — RPI's Research phase relies on the instruction "document only, don't prescribe" as a behavioral rule rather than a structural information-hiding one (rpi-framework.md §2).
- **Team-scale origin vs. solo-scale framing.** RPI was literally born to solve a team code-review bottleneck (rpi-framework.md §1). Wayfinder's own author frames it around a single engineer's context management (wayfinder-prototype.md §5). QRSPI variants split on this axis themselves (qrspi.md §4-5). This means "which is built for a team vs. a solo engineer" doesn't have one answer across the three — it varies inside QRSPI's own variant set as much as it does between RPI and Wayfinder.

## 5. Usability Verdict — Is One More Usable Than the Other?

**No single answer — usability is conditional on the shape of the work, not a fixed ranking.** Each has a real, documented usability weakness alongside its strength:

- **RPI** has the lowest setup cost — 3 slash commands, no external infrastructure, no tracker dependency (rpi-framework.md §6). Its weakness is that its own tooling documentation is internally inconsistent: Kilo's docs and Goose's own docs cite different command name strings (`/research` vs `/research_codebase`) for what's claimed to be the same tool, and neither source resolves which is current (rpi-framework.md §5). Anyone copying RPI's commands verbatim from a secondary source risks copying stale or paraphrased names.
- **Wayfinder+Prototype** has the most production-grade distribution — an official, actively-maintained Claude Code marketplace plugin (wayfinder-prototype.md §5). Its weakness is the heaviest setup burden of the three (a tracker must be configured via `/setup-matt-pocock-skills` before wayfinder, to-spec, or to-tickets function at all) and a documented reliability gap: the repo's own docs admit "a skill that names another skill does not reliably cause that skill to load" (wayfinder-prototype.md §4) — meaning the skill-chaining design the whole pipeline depends on (`grill-with-docs` calling `grilling` + `domain-modeling`, `wayfinder` calling the same pair) isn't guaranteed to actually fire in practice.
- **QRSPI** is the hardest to adopt with confidence, precisely because there is no single canonical version to point at — 4+ independently-built repos with different phase counts, no adoption metrics found for any of them (qrspi.md §1, §4-5). Its usable core (hide-the-ticket, ~200-line design cap) is real and cheap, but the framework as a packaged whole is not something a newcomer can install and trust the way they can trust RPI's two documented reference implementations or Wayfinder's marketplace plugin.

**For this specific user** — a solo engineer already running Claude Code with an existing `me-draft`/`me-craft` pipeline in this repo — RPI's minimal 3-command shape is the most usable to bolt on incrementally: it needs no new infrastructure, and it maps 1:1 onto an existing skill boundary (a Research sub-step feeding `me-draft`'s Phase 1, see Section 6). Wayfinder is more usable specifically for genuinely multi-session, foggy-scope efforts, which is a narrower slice of day-to-day work than routine ticket implementation. QRSPI's two cherry-picked ideas (ticket-hiding, size cap) are usable in isolation; QRSPI as an installed framework is not recommended given the fragmentation above.

## 7. Recommendation — Adopt, Adapt, or Run Side-by-Side

**Verdict: adapt, don't adopt wholesale — extend `me-draft`/`me-craft` with the two or three cheapest, best-corroborated mechanics; hold off on any new top-level skill until a real multi-session-foggy-project need shows up.** This follows `rules/craft-style.md`'s "spike unknown territory before committing" and `rules/decision-gates.md`'s Clarity Gate — building speculative infrastructure ahead of a demonstrated need is exactly the failure mode those rules exist to catch.

1. **Extend `/Users/duy.ton/Documents/Workshop/my-agents.feat-rpi/skills/me-draft/SKILL.md`, Phase 1** to optionally persist a standalone research sub-artifact (e.g., `thoughts/research/YYYY-MM-DD-topic.md`) before Phase 2's plan doc, gated by the same "skip for small changes" clause the skill already has. When this sub-step runs, hide the raw ticket/requirement from it — QRSPI's one mechanical, cross-variant-corroborated anti-bias trick (qrspi.md §5) — and confirm only actual code facts before Phase 2 reintroduces the requirement. This is a template edit to an existing file, not a new skill.
2. **Add a soft ~200-line cap to `me-draft`'s "Plan Structure" template** (the same file, Phase 2 section). This number is independently corroborated across three unrelated QRSPI implementations (jaeyunha, earlmundorf, and Horthy's own talk per alexlavaee.me — qrspi.md §3) as the point where a plan stays reviewable without becoming as much work to read as the diff itself.
